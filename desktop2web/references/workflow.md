# 共通ワークフロー規則（desktop2web）

legacy-reverse の references/workflow.md を全面的に継承する（ISSUE運用・承認ゲート・
ハッシュ連鎖・人の直接入力スキャン・レンダリング）。本書は差分のみ。

## 2レーンの情報遮断

| 作業 | 読んでよい | 読んではいけない |
|---|---|---|
| ⓪ 解析 | legacy/ 全部 | — |
| Ⓐ 方針 | ⓪の成果物（screens/functions/schema/CRUD）、旧画面のスクリーンショット | — |
| 画面票の起票・モック | 方針書、旧画面スクショ、画面票、⓪の uses 情報 | **機能の実装(backend/src)**（APIコントラクトのみ参照） |
| 画面実装 | design-fixed の画面票、方針書、機能レーンの**公開API**（①仕様書のシグネチャ） | legacy/ |
| E2E作成 | 画面票の受け入れ基準のみ | 画面実装の内部 |
| 機能レーン①〜⑤ | legacy-reverse の規則どおり | 同左 |

- **画面レーンはビジネスロジックを書かない。** バリデーション・計算・絞り込み条件などを
  モック中に「仮実装」したくなったら、それは⓪の抽出漏れ → 機能として functions.json に
  追加起票し、鏡移しレーンへ回す（ISSUE で記録）

## 画面イタレーションのループ規律

1. モック（`frontend/mocks/S-xxxx/v<N>.html`）は**静的HTML＋Tailwind CDN**で作り、
   ブラウザで人に見せる。試行錯誤はここで安く回す（承認不要、版だけ票に記録）
2. レビュー指摘は画面票の「モック履歴」表に必ず転記（口頭指摘を揮発させない）
3. **design-fixed が承認ゲート**。確定後は受け入れ基準を凍結し、E2E を書いて freeze
4. design-fixed 後にデザインを変えたくなったら ISSUE → 人承認 → mock-review に差し戻し
   （票の版数は続きから。E2E は再生成→再freeze）
5. E2E fail 時のトリアージは機能レーン⑤と同型:
   (a) 画面実装のバグ → 直す（デフォルト） / (b) E2E が受け入れ基準とズレ → ISSUE→承認
   / (c) 受け入れ基準・機能仕様が誤り → ISSUE→承認→上流改訂
6. 上限3回で ISSUE 自動起票・ブロックの規律も機能レーンと同じ

## スケジューリング（プル型）

- 次にやる画面（WBS推奨順: 依存機能が少ない画面から）を決める
  → その `uses` の未完了機能が機能レーンの「次やるべき①」に浮上する
- 機能が⑤passするまで画面実装は着手しない（モック・design-fixed までは並行してよい）

## UX再設計の指針（Ⓐでプロジェクト別に上書き）

デスクトップ由来の棚卸し観点: モーダルダイアログの連鎖 / グリッド偏重 / 検索ボタン押下式
（→即時絞り込み）/ Tab移動前提のフォーム / 画面分割がDB都合 / エラーのメッセージボックス
（→インライン表示）。旧画面の「なぜこうなっていたか」を票に書き、Webでの解を提案する。

## レンダリング

- 各フェーズ末: `d2w_ledger.py wbs`（画面＋機能の統合WBS）→ `quarto render docs`
- CRUDマトリクスは `d2w_ledger.py crud` で docs/crud.md を再生成
- モックのレビューは静的サーバ（`python -m http.server --directory frontend/mocks`）＋
  ブラウザペインで実施

# d2w-policy — Ⓐ 方針決定（全体で1回）

親skill desktop2web の references/ に従う。前提: ⓪完了。
**このフェーズは「AIが案を出し、人と対話して決める」フェーズ。** 勝手に確定しない。

## 手順

1. ⓪の成果物（screens.json / crud.md / スクリーンショット）を読み、
   `assets/templates/policy.md` を土台に**概案を2〜3案の比較で**作る:
   - **新画面マップ**: 旧画面の統合・分割案。「DB都合/デスクトップ都合で分かれていた画面」を
     特定し、Webでの再編を提案（例: 一覧＋詳細ダイアログ → 一覧＋サイドパネル）。
     案ごとに画面数・ナビゲーション構造を figure（Mermaid可）で示す
   - **APIコントラクト方針**: 機能(F-xxxx)をどうAPIに束ねるか
   - **デザインシステム**: Tailwind トークン、共通コンポーネント、UXの原則
     （workflow.md の棚卸し観点を旧画面に当てた結果を添える）
2. 概案をチャット＋HTMLで提示し、人の選択・修正を受けて docs/policy.md に落とす
3. 人のOKで status: approved に更新。**新画面マップを screens.json の `screens` に反映**し、
   `d2w screen-skeletons` で画面票の骨子を生成、`d2w wbs` → quarto render
4. 画面イタレーションの推奨順（`d2w next` の初期提案）を方針書末尾に記載

## 決めずに進んではいけないこと

- 新画面マップ（以後のWBSの行が決まる）
- UXの原則（全モックの判断基準になる）
- APIコントラクト方針（機能レーンのシグネチャ設計に影響）

## 禁止

- 人のOKなしで approved にすること
- 旧画面の1:1コピーを既定にすること（再編を検討した痕跡を必ず残す。
  1:1のままにするなら「なぜそれが最善か」を書く）

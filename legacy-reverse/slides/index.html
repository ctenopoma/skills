ツール概要

レガシーコードから仕様書・テスト仕様書を作成し、それに基づき実装・テストをAIエージェントが自律的に実行します。

⓪ 解析関数リスト
→
⓪ 辞書変数の意味
→
① 仕様書人がOK
→
② テスト仕様人がOK
→
③ テストコード
→
④ 実装
→
⑤ テスト突き合わせ

コードも仕様もAIエージェントが作成し、人は以下の4つだけを担当します。

人の作業内容場面
1. 実行するフェーズを起動する（チャットのコマンド、または pipeline.py）各フェーズの最初
2. 質問に回答するAIからの質問（ISSUE）に回答する随時
3. 承認する⓪の変数辞書・①の仕様書・②のテスト仕様に OK を出す⓪・①・②
4. 判断する⑤でテストが落ちたとき、原因の種類を決める⑤で fail のとき
機械的な検証をクリアして初めて人の承認フローに進みます。 また人の承認なしに仕様は確定しません。

操作と閲覧

HTML の進捗サイトは閲覧専用です。実行・承認はチャットか CLI で行い、 画面には状態と「どう返答するか」の案内が出ます。返答チャネルは3つで、どれでも同じです。

コマンド自動実行—pipeline.py run / spec / testspec / testcode / impl / test
承認・修正依頼「F-0012 OK」「修正: 〜」review_actions.py approve / request-changes・review-feedback.md に記入
質問への回答・裁定チャットで答えるISSUEファイルの回答欄に記入・review_actions.py adjudicate
変数辞書の承認「V-0001 を承認」variables.py approve / revise

  3. 人の作業: ヒアリングに回答する。⓪のうちに3つの Markdown を埋める

⓪のレガシーコード解析：例外ポリシー

FortranとPythonには言語間でのギャップが存在します。

例えばFortran は0で割っても Inf（無限大）を作って走り続けますが、Python はそこで エラー落ちします。平方根の負値・対数の0にも同じことが起きます。そのまま移植すると 動きが変わるので、①より先に扱いを決めます。

該当箇所は⓪が機械で洗い出し、「0割が N 箇所あります。既定をどうしますか」と種類ごとにまとめて聞かれるので、種類ごとに回答して反映させます。

答え意味
guard_raiseチェックして例外を出す
guard_value代わりの値を返して続行
legacy_preserveInf/NaN のまま流す（レガシー再現）
detect_only仕様書に書くだけ
caller_guarantees呼び出し元が保証している
既定は guard_raise です。 「F-0012 のここだけは呼び出し元が保証」のようにも回答できます。

移行対象の設定

①以降のバッチは、既定では全関数が対象です。メインルーチンが複数ある、 または main に大きな分岐があって系統ごとに別々に進めたい場合は、 フローを定義すると「その Main から呼ばれて到達できる関数だけ」に絞ってください。

  1. ⓪の途中で「作業スコープを分けますか」と聞かれたら、Mainの 関数IDと呼び名を答える（例:「F-0000 を Main」）。 後からコマンドで定義も可能。 
    python <LR>/scripts/ledger.py --root . flow add <フロー名> --entry F-0000
python <LR>/scripts/ledger.py --root . flow list      # 定義の確認
  2. 以後のバッチに --flow <フロー名> を付けるだけ: 
    python <LR>/scripts/pipeline.py spec --root . --flow <フロー名>
    spec / run / testspec 等すべてで使え、 「次の一手」も ledger next --flow <フロー名> で絞れる
  • Mainから到達可能な関数の絞込は呼び出し関係から自動で取得する。

⓪ 変数辞書 (2/2)

  1. skillを実行する:Claude Codeを起動し、次の/コマンドを実行する 
    /legacy-0-dict
  2. AIエージェントが根拠から変数の意味を書き、 機械が検証して辞書ページ（進捗サイトの「変数辞書」）を更新する
  3. 承認する: ブラウザでナビバーの「変数辞書」を開く。 変数が「多くの関数で使われるもの・確認が要るもの」順に並んでいるので、上から:
    行の表示操作
    rank A / B（コメント等の根拠あり）意味を確認してチェック→一括承認

意味が「不明」のままでも承認さえすれば①に進めます。逆に 未承認の変数が残る関数は①の対象から外れます（dict-gate。急ぐときは ledger next --no-dict-gate で解除）。

仕様書の様式 — docs/templates/

①②の項目立て（節の構成）はプロジェクトの持ち物です。⓪の init-templates で雛形が置かれるので、①を始める前に確定させます。

ファイル決めるものいつ
docs/templates/spec.md ①関数仕様書の節構成・各節の記入ガイド①の前
docs/templates/test-spec.md ②テスト仕様書の節構成・ケースの書式②の前
後から節を足すと、書き終えた仕様書が全件やり直しになります。 機械レビューの必須節はテンプレの「# 見出し」から導かれるので、①のあとに節を 増やすと既存の仕様書が一斉に「必須節がない」＝❌になります（＝承認できない）。
  • 節を足す・消す・記入ガイドを書き換えるのは自由。書くのは人だけ（AIは提案まで）
  • ただし固定契約は消せません——①は <!-- LR:IO-TABLES --> 等の置換マーカーと 「# 機能詳細」「# 副作用・例外」「## 例外・数値特異点」「# 未確定事項」、 ②は「# トレーサビリティマトリクス」とケースID・「対応仕様」「期待値の根拠」
  • 直したら確認コマンドで固定契約の欠けを見る: 
    python <LR>/scripts/review_checks.py template --root .

AIへの指示 — docs/prompts/

①〜④は起動のたびにその工程のファイルを読んでから書き始めます （1件ずつ・全件バッチ・作り直しのいずれでも同じ）。効くのは次の実行からなので、 その工程のバッチを流す前に書きます。 書き終えた成果物には遡って効きません（直すには再実行が必要）。

ファイル効く工程いつ書くか記載例
docs/prompts/1-spec.md① 仕様書 ①の全件バッチの前 「漸化式は言葉で要約せず式で書く」「添字の基準を毎回明記」
docs/prompts/2-testspec.md② テスト仕様 ②の全件バッチの前 「0近傍と負値は全関数で必ず1ケース」
docs/prompts/3-testcode.md③ テストコード ③④⑤を流す前 「fixture は conftest.py に集約」「比較は pytest.approx」
docs/prompts/4-impl.md④ 実装 ③④⑤を流す前 「要素ごとの Python ループは避ける」「Decimal を float にしない」
書きどき（工程ごとに同じ形）
  1. 1件だけ試す（/legacy-1-spec F-0001）→ 出てきた成果物を読む
  2. 「毎回こう書いてほしい」を その工程の prompts に書く。 各ファイルには 重点 / 用語の約束 / 繰り返さないでほしい指摘 / 手本にする成果物 の節がある。最も効くのは「手本」—— 「粒度は docs/specs/F-0123.md に揃えて」の1行が、抽象的な指示10行より揃う
  3. 全件バッチを流す
指摘の射程で書き分ける
  • この1件だけ直したい → チャット、または修正依頼
  • 毎回同じことを言っている → prompts の「繰り返さないでほしい指摘」に1行。 節そのものを増減したいなら docs/templates/、規約なら conventions.md
  • skill 自体の不備・機械で判定できる指摘 → skill 側の検査に足す（全プロジェクトに効く）

雛形のままなら「指示なし」。書けるのは「どう書くか」だけで、読んでよい入力の制限・ 必須項目・承認の要否といった土台の規則は変えられません （反する指示があっても AI は従わず、人に報告します）。

① 関数仕様書

  1. まず1関数だけお試し: ClaudeCodeを起動し次の/コマンドを実行する 
    /legacy-1-spec F-0001
    （関数IDはWBSの推奨着手順の先頭から）。
  2. 出てきた仕様書を読んで、規約や変数辞書の効き方に問題がないか品質を確かめる。 直したい傾向があれば、ここで規約・辞書・docs/prompts/1-spec.md（前ページ）を 直してから全件へ。
  3. 全件バッチ: 
    python <LR>/scripts/pipeline.py spec --root .            # 全関数
    夜に起動して寝てよい。機械レビュー通過済みの draft が溜まっていく
  4. 人がやること: 一斉レビュー表（次ページ）で まとめて承認する。各項目の Confidence（🟢確認済 / 🟡推測 / 🔴仮定）が 目印。🟡🔴の質問には Yes/No で答える（答えられなければ「保留」でよい）
提示される仕様書は機械レビュー通過済み: 引用行の実在・記入漏れ・根拠なし🟢は機械が先に落としている。 あなたは「意味が正しいか」だけを見ればよい。 最終品質の上限はこのレビューの品質です——いちばん丁寧にやる価値がある場所。

②へは、①のレビューが終わってから進むのが基本形 （②は「①が承認済みの関数」しか対象にならないので、順序は仕組みでも守られる）。 書き直しは draft のうちは何度でも頼める。

一斉レビュー表

承認待ちの成果物が1枚の表に並びます。①と②に1枚ずつあり、 どちらも WBS の「要対応」からリンクされます。表は閲覧専用で、 承認・修正依頼は次ページの3チャネルで返します。

表載るもの固有の列
① /spec-review.htmldraft の仕様書 概要・Confidence（🟢確認済 / 🟡推測 / 🔴仮定 の件数）
② /testspec-review.htmlgenerated のテスト仕様書 テスト方針・ケース数・⚠未確定の件数

共通の列は 機械レビュー（✅ / ❌。クリックで成果物ページの案内パネル＝ NG理由の全文へ飛ぶ）・未確定(ISSUE)・状態です。

  • 並び順が優先度: 承認できる → ISSUE がある → ⚠回答待ち → AI修正待ち。 判断が要らないものから片付けられる
  • ❌ の行は人が承認できない（どの入口から要求しても拒否される）。 AIの自己修正を待つ
  • ②の⚠回答待ちは期待値が決まっていない行。質問に回答するまで承認できない
  • 各行の高さには上限があり、長い行はカーソルを載せると開く（表が縦に伸びない）

承認と修正依頼

①仕様書・②テスト仕様書への返答は3チャネルあり、どれでも結果は同じです （<種別> は①なら spec、②なら testspec）。

チャネル承認修正依頼
チャット「F-0012 OK」「全部OK」 「F-0012 修正: 端数処理が書かれていない」
CLI review_actions.py approve <種別> F-0012 --by 名前 --root . review_actions.py request-changes <種別> F-0012 --by 名前 --comment "…" --root .
ファイル記入—（承認はファイル記入では行わない） docs/review-feedback.md に追記する
# docs/review-feedback.md に人が直接書く場合（request-changes と同じ書式）
## F-0012（spec）
- 起票: 2026-08-21T10:00:00 / 山田
- 状態: pending
- 内容: 端数処理の丸め方向が書かれていない
  • 承認は機械レビューを再検証してから通る。❌が残っていれば チャットでも CLI でも拒否される
  • 修正依頼は状態: pending で残り、次の /legacy-1-spec F-0012 や pipeline.py run が拾って反映し、状態: applied に書き換える
  • どの経路でも、反映後に WBS・一斉レビュー表・サイトの再生成まで自動で走る

仕様書ページの先頭にはその関数用のコマンドが焼き込まれた案内パネル が出ます（機械レビュー結果の全文つき）。コピーして実行すれば、上の表を覚える必要はありません。

② テスト仕様書

  1. 先に様式と指示を決める: docs/templates/test-spec.md（項目立て）と docs/prompts/2-testspec.md（書き方）。①と同じくバッチの前に 確定させる（1件だけ試してから全件、が安全）
  2. 全件バッチ: 
    python <LR>/scripts/pipeline.py testspec --root . [--flow <フロー名>]
    対象は①が承認済み（reviewed）の関数だけ。未承認の関数が勝手に進むことはない。 1件ずつなら /legacy-2-testspec F-0001
  3. 実施事項: AIが「①の仕様書だけ」からテストケースを設計する （レガシー原文は見ない。①に書いていないことはテストにできない＝仕様書の穴がここで出る）
  4. 人の作業:
    • ケース一覧（正常系・境界値・異常系）を確認する
    • 期待値が決められないケース（⚠未確定）の質問に回答する
    • 承認する（⚠未確定が残ったままの承認は機械が拒否する）

「全🟢仕様項目にテストがあるか」「①に無い仕様IDを作っていないか」は機械検証済み。 人は期待値が業務的に正しいかを確認する。全件バッチのあとは ②の一斉レビュー表（/testspec-review.html）でまとめて承認する。

ここまでで人の承認は完了。③④⑤に承認ゲートは無いので、次はまとめて流すだけです。

③④⑤ 実行

②の承認が済んだ関数は、③テストコード→④実装→⑤テストまで人の承認なしで進みます。 全件流すには:

python <LR>/scripts/pipeline.py run --root . [--flow <フロー名>]

run は「次に進められる工程」を関数ごとに自動判定するので、③④⑤を分けて指定する 必要はない（分けたければ --only testcode 等）。 1件ずつなら /legacy-3-testcode F-0001 / /legacy-4-impl F-0001。

③と④はそれぞれ独立に作られます:

③ テストコード入力は「②＋規約」だけ
⇄互いを見ない
④ 実装入力は「①＋規約」だけ
  • ③完了時にテストは freeze（ハッシュ記録）。以後AIがテストを書き換えようと しても hook が拒否する（「テストを緩めて通す」事故を仕組みで防ぐ）
  • ④のスタブ（空実装・TODO）は機械検知されるので「実装したふり」はできない
  • ④が「①だけでは決められない」と気づくと ISSUE を起票して止まる → 人は質問に回答するだけ（①の改訂・伝搬は自動で処理される）

⑤ の結果と判断

⑤はバッチ（run）が自動実行します（1件ずつなら /legacy-5-test F-0001）。 pass なら完了（WBS が ✅）。fail のときだけ人が原因の種類を決めます。

分類原因人の操作
(a) 実装バグ実装が①を満たしていない 何もしない（AIが src/ を修正して再実行する）
(b) テストのバグ③が②とズレている ISSUE に回答 → ③を再生成（/legacy-3-testcode）
(c) 仕様が誤り②①自体が間違い ISSUE に回答 → ①を改訂（/legacy-1-spec）→ ②③へ伝搬

(a) の自動修正は3回連続で fail すると停止し、AIの失敗分析（何を試し、なぜ駄目で、 (a)/(b)/(c) のどれと考えるか）を書いた ISSUE が自動起票されて WBS に ⛔ が出ます。

  1. 仕様書ページ先頭の⛔案内パネル（バッチ状況の「人待ち」からも開ける）に 質問と返答方法が出るので、回答する 
    python <LR>/scripts/review_actions.py adjudicate F-0012 --issue ISSUE-004 --by 名前 --comment "回答…" --root .
    チャットなら「ISSUE-004 は〜が正」でも同じ（AIが記入・unblock まで行う）
  2. 回答が入ると unblock され、⑤を再実行すると反映される （/legacy-5-test F-0012 または pipeline.py run）
⛔ は人の回答待ちで完全に止まっている状態。見かけたら最優先で回答する。 (b)(c) をAIが勝手にやることはない（テスト改変は hook が拒否する）。

全件バッチの共通ルール

pipeline.py spec / testspec / run は、すべて同じ性質を持ちます:

  • いつ止めても安全、再開は同じコマンド。 Ctrl-C・電源断でも進捗は すべてファイル側にあり、もう一度同じコマンドを打てば続きから走る
  • レートリミット・利用枠上限は待って自動再開。 失敗扱いにせず 指数バックオフで待つので、夜間の利用枠リセットを人手なしで跨げる
  • 承認待ち・回答待ちは自動でスキップして先へ進む＝ 人が承認する速度が全体の速度。回しながら一斉レビュー表・ 「人待ち」タブで承認していく
  • 1関数=1つの新しいAIプロセスなので、何千件でもトークン上限に当たらない

よく使う操作:

python <LR>/scripts/pipeline.py run --root . --dry-run    # 実行せず対象と順番だけ確認
python <LR>/scripts/pipeline.py run --root . --max-funcs 20  # 今日は20件だけ
python <LR>/scripts/pipeline.py priority F-0012           # この関数を次に割り込ませる（実行中でも効く）
python <LR>/scripts/pipeline.py priority                  # ⭐割り込みの一覧（--off / --clear で解除）

ISSUE の回答

AIが判断に迷うと ISSUE（質問票）を docs/issues/ISSUE-xxx.md に起票します。 必ず「仮説＋Yes/Noで答えられる問い」の形で、白紙の質問は来ません。

事象（根拠つき）→ 質問（仮説＋問い）→ 回答（人が記入） → 反映

チャネルやり方反映のタイミング
チャット「ISSUE-004 は Yes」「ISSUE-004 は No。〜が正しい」 その場（AIが回答欄に記入 → 成果物へ反映）
ファイル記入 ISSUE-004.md の「回答（人が記入）」にある - 回答: と - 回答者 / 日付: に書く 次に skill を起動したとき（起動時スキャンが拾う）
CLI（⑤の裁定） review_actions.py adjudicate F-0012 --issue ISSUE-004 --by 名前 --comment "…" その場（記入 → unblock まで）
  • 状態は open →（人が回答）answered →（成果物へ反映）applied と進む
  • 業務知識として残る回答は AI が転記文を提案する。 docs/domain-knowledge.md に貼るのは人（AIは書き込まない）。 貼れば同じ質問は二度と来ない
  • 未回答の ISSUE は WBS の「Open ISSUES（要人間判断）」に出続ける。 ⛔ が付いた関数は回答待ちで止まっている

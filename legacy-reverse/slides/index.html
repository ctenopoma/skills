はじめてガイド

legacy-reverse
初めて使う人のための操作ガイド

レガシーコード（Fortran / C 等）を Python へ移植するツールです。
このスライドを上から順に読んで、書いてあるとおりに操作すれば、 セットアップから移植完了まで進められます。

→ キーで次へ / ← で戻る / 右上「一覧表示」で通し読み

これは何をするツール？ — 流れを1枚で

レガシーを「読んで直接書き写す」のではなく、間に仕様書を挟みます。 仕様書からテストと実装を別々に作り、最後に突き合わせる—— 一致すれば、仕様書どおりに移植できた証拠になります。

⓪ 解析関数リスト
→
⓪.5 辞書変数の意味
→
① 仕様書人がOK
→
② テスト仕様人がOK
→
③ テストコード
→
④ 実装
→
⑤ テスト突き合わせ

この ⓪→⑤ を関数ごとに繰り返し、 全関数が終わったら ⑥ 完了検証 → ⑦ 分析・改善

前提: レガシーを動かせる環境は無くてよい。 「レガシーを実行して出力を比べる」方式ではありません。正しさは (1) 人が仕様書をレビューして確定すること、 (2) その仕様書だけから独立に作ったテストと実装が⑤で一致すること、で担保します。

あなたの仕事は4つだけ

コードも文書も、あなたが直接書く必要は基本ありません。 AIが書く、機械（スクリプト）が検証する、あなたが決める——という分担です。

あなたの仕事具体的には登場する場面
1. トリガを引くフェーズを起動する（チャットのコマンド、または pipeline.py）各フェーズの最初
2. 質問に答えるAIからの質問（ISSUE。仮説＋Yes/No形式）に回答する随時
3. 承認する⓪.5の変数辞書・①の仕様書・②のテスト仕様に OK を出す⓪.5・①・②
4. 裁定する⑤でテストが落ちたとき、原因の種類を決める⑤で fail のとき
あなたのOKなしに仕様は確定しません。逆に、機械の検証を通っていないものが あなたのところへ届くこともありません（NG付きの成果物はどの入口からも承認できない作りです）。

基本の運転モデル: フェーズごとに Python の無人バッチで 全件を流し、溜まったものをまとめて承認する、の繰り返しです（①を全件→まとめて承認→ ②を全件→…）。1件ずつ進めるのは、最初に流れを掴むお試しのときだけ。

操作はチャットと CLI、ブラウザは「見る」専用

HTML の進捗サイトは閲覧専用です。実行・承認はチャットか CLI で行い、 画面には状態と「どう返答するか」の案内が出ます。返答チャネルは3つで、どれでも同じです。

やることチャットCLI / ファイル記入
フェーズを起動/legacy-1-spec F-0001 等のコマンド—
まとめて無人実行—pipeline.py run / spec / dict
実行順の割り込み—pipeline.py priority F-xxxx
承認・修正依頼「F-0012 OK」「修正: 〜」review_actions.py approve / request-changes・review-feedback.md に記入
質問への回答・裁定チャットで答えるISSUEファイルの回答欄に記入・review_actions.py adjudicate
変数辞書の承認「V-0001 を承認」variables.py approve / revise

このガイドでは基本を「Python の無人バッチで流して、ブラウザで まとめて確認し、チャット / CLI で承認する」という流れで説明します。 進捗サイトの開き方は⓪が終わったところで出てきます。

必要なもの確認コマンド
Claude Code の CLI が PATH にclaude --version（無人バッチは裏でこれを呼ぶ）
Python 3.10 以上python --version
移植先プロジェクトが git 管理下git status

skill のコピー（cwd は skills リポジトリの中）:

cd <skills>                                    # このリポジトリを clone した場所

2行必要です。1行目が skill 本体一式、2行目はフェーズ別 skill を .claude/skills/ の直下にも置くため（Claude Code はここを見て /legacy-1-spec を認識する）。中身が重複しますが、これで正しい状態です。

以降このスライドでは <LR> = <project>/.claude/skills/legacy-reverse（コピー先）を指します。 コマンドは断りがなければ <project> の中で実行します。

セットアップ② — hook・MCP・ツール類

1. hook を登録（必須） — <LR>/hooks/settings-example.json の内容を <project>/.claude/settings.json へマージ。2本入っています:

  • guard_tests.py — 「AIがテストを書き換えて通す」事故を防ぐ
  • guard_json.py — 「AIが関数リスト(JSON)を壊してバッチが止まる」事故を防ぐ

2. MCP サーバを登録（推奨） — MCP は AI に外部プログラムを「道具」として 渡す仕組み。登録すると実行のたびに出る許可ダイアログが減り、失敗も減ります （未登録でも動作は同じ）。<project>/.mcp.json を作って:

{
  "mcpServers": {
    "legacy-reverse": {
      "command": "python",
      "args": ["C:/work_space/skills/mcp-servers/legacy-reverse-mcp/server.py"]
    }
  }
}

パスは <skills> の絶対パスに置き換えてください （上は例）。ここだけコピー先ではなく元のリポジトリを指すので、 セットアップ後もリポジトリを消さないでください。

3. ツール類 — Quarto（進捗サイトの生成に必要。 quarto.org のインストーラで入れる。quarto --version が通ればOK）と pip install pytest sphinx sphinx-rtd-theme。

管理者権限を使いたくなければ python <skills>/quarto-typst-pdf/scripts/qtpdf.py install でポータブル導入も可。 合本PDFまで出すなら、あとで quarto-typst-pdf/ も .claude/skills/ にコピーします（HTMLだけなら不要）。

4. 無人バッチの実行許可（重要） — このガイドの基本線である無人バッチは 許可ダイアログに答えられないため、先に許可を通しておきます。方法は2つ:

  • <project>/.claude/settings.json の permissions.allow に Read / Write / Edit / Bash を許可しておく
  • 信頼できる閉じた環境なら、バッチ起動時に --skip-permissions を付ける （共有マシンでは使わない）
準備ができたら Claude Code を開き直して /legacy-reverse と打つ。 セットアップ状態を確認して、次にやることを案内してくれる。 以後も、迷ったら・再開するときは、いつでも /legacy-reverse。

セットアップ③ — あなたが書く MD を用意する

「どう進めるか」（工程・チェック・禁止事項）は全プロジェクト共通で固定です。 一方「このプロジェクトでどう書くか」は、あなたが MD に書いて決めます。 その置き場所は⓪の最初に自動で作られます（/legacy-0-analyze が 下のコマンドを実行します。手で打つ必要はありません）。

python <LR>/scripts/ledger.py --root . init-templates   # 雛形を一式配置（既存は上書きしない）
python <LR>/scripts/ledger.py --root . authored         # どこがまだ未記入かを一覧

白紙は作られません——どのファイルにも空欄と「何を書くか」の 記入ガイドがコメントで入っています。AI はそのガイドを質問の台本として使い、あなたの回答を 記入文として提示します（貼って確定するのはあなた）。

置き場所書くこといつ書くか
docs/conventions.md 規約: 型対応表・丸め・許容誤差・単位・日付・命名・docstring ⓪のヒアリングで決め切る
docs/domain-knowledge.md 業務知識: 略語・区分値・ISSUE に答えた内容 ⓪で語彙を先に。以後は随時
docs/templates/ 仕様書の項目立て（節を足す・消す・記入ガイド） ①を始める前
docs/prompts/ 工程ごとのAIへの指示（重点・用語・繰り返さない指摘・手本） いつでも（次の実行から効く）
書き方の要点
  • 丸め・許容誤差・単位・日付・文字コード・既知バグの扱いは⓪で決め切る。 ②以降の全ケースの期待値の前提になるので、後から覆すと作り直しになります
  • 迷ったら「関数ごと」ではなく全体の既定を1つ。例外は domain-knowledge.md に関数単位で書けば、そちらが勝ちます
  • docs/prompts/ は雛形のままなら「指示なし」。必要な工程だけ書けば十分

AI はこれらのファイルを書き換えません（直したほうがよい時は提案文を出すだけ）。 あなたの決めたことと AI の文章が混ざらないようにするためです。 authored は ✗未作成 / ・未記入（雛形のまま）/ ▲記入途中（{{…}}が残り）/ ✏記入あり を表示します。

⓪ 解析 — 関数リストを作る

  1. 打つ: /legacy-0-analyze
  2. 起きること: 静的解析プログラムがレガシーの全関数を機械抽出する （Fortran / C。引数・COMMON・呼び出し関係・外部ファイルまで自動。AIは説明の充填だけ）
  3. あなたがやること: ヒアリングに答え、⓪のうちに3つの MD を埋める （AI が質問リストと記入文を出すので、貼って確定するのがあなたの作業）
    埋める MD聞かれること後回しにすると
    docs/conventions.md レガシーの場所・言語・新パッケージ名、型対応表（例: REAL*8→float）、 丸め・許容誤差・単位・日付・文字コード・既知バグの扱い ②以降の期待値の前提。後から覆すと②〜⑤が作り直し
    docs/domain-knowledge.md 「この略語は読めますか」——ZAN・KBN 等の語彙・略語と 区分値（KBN=9 はエラー等）。分かるものだけでよい 次の⓪.5で変数辞書の一括承認が効かなくなり、1件ずつ見る量が増える
    docs/exception-policy.md 「0割をどう扱うか」（次ページ。登録はコマンドで行う） 未決定のままだと①に進めない（機械レビューが止める）
完了のサイン: 関数一覧（functions.json）と進捗サイトができ、 関数数・循環の有無・推奨着手順が報告される。最後に「次は /legacy-0-dict」と案内される。

数え漏れは2系統カウントの突合で機械検知。不明点は ISSUE（質問）としてあなたに来る。 途中でやり直しても安全（再実行はマージ動作。関数IDは変わらない）。

⓪の途中で聞かれること — 例外ポリシー（0割の扱い）

Fortran は0で割っても Inf（無限大）を作って走り続けますが、Python はそこで 止まります。平方根の負値・対数の0にも同じことが起きます。そのまま移植すると 動きが変わるので、①より先に扱いを決めます。

検知は機械、決定はあなた。該当箇所は⓪が機械で洗い出し、 「0割が N 箇所あります。既定をどうしますか」と種類ごとにまとめて聞いてきます。 1箇所ずつではなく、種類ごとに1回答えれば全箇所に効きます。

答え意味使いどころ
guard_raiseチェックして例外を出す 迷ったらこれ。異常を握り潰さない
guard_value代わりの値を返して続行 業務上「0のときは0扱い」等が決まっている場合（値も伝える）
legacy_preserveInf/NaN のまま流す（レガシー再現） 下流が Inf を前提にしている場合
detect_only仕様書に書くだけ 実際には起こり得ないが記録は残したい場合
caller_guarantees呼び出し元が保証している なぜ保証されるのかも伝える（根拠が要る）
あなたがやること:「既定は guard_raise、 ただし F-0012 のここだけは呼び出し元が保証」のように答える （個別の指定が全体の既定に勝つ）。答えは登録簿に記録され、二度と聞かれない。

作業範囲を決める — 「この Main に関わる範囲だけ」を指定できる

①以降のバッチは、既定では全関数が対象です。メインルーチンが複数ある、 または main に大きな分岐があって系統ごとに別々に進めたい場合は、 フローを定義すると「その Main から呼ばれて到達できる関数だけ」に絞れます。

あなたがやること:
  1. ⓪の途中で「作業スコープを分けますか」と聞かれたら、Main（エントリ）の 関数IDと呼び名を答える（例:「F-0000 を『月次バッチ』、F-0031 を『日次』で」）。 聞かれなくても、後からいつでも次のコマンドで定義できる: 
    ledger flow add 月次バッチ --entry F-0000
ledger flow list                        # 定義の確認
    エントリは main そのものでなく「分岐先の代表サブルーチン」でもよい
  2. 以後のバッチに --flow 月次バッチ を付けるだけ: 
    python <LR>/scripts/pipeline.py spec --root . --flow 月次バッチ
    spec / run / dict すべてで使え、 「次の一手」も ledger next --flow 月次バッチ で絞れる
  • 範囲（到達集合）はコールグラフから自動計算される。あなたが関数を 列挙する必要はないし、レガシーを再解析しても自動で追随する
  • 定義すると WBS に「フロー別進捗」表が出る（系統ごとの進み具合が見える）
  • 全関数を一気にやるなら定義しなくてよい（このスライド以降の --flow は省略すれば全関数が対象）

記号意味あなたの対応

⓪.5 変数辞書 (1/2) — なぜ仕様書より先にやるのか

レガシーの変数名（R8TBL・WKA・IFLG）はそれだけでは 意味が分かりません。しかも同じ変数が COMMON 経由で10も20もの関数に顔を出します。 意味を決めないまま仕様書を書くと、同じ変数に関数ごとに違う説明が付き、 後で直すにはレビュー済みの仕様書を全部開き直すことになります。

だから①より先に、ここで「1変数＝1つの意味」をあなたが確定させます。 機械が「同じ実体」をまとめてくれているので、 1回承認すれば、その変数が出てくる全関数に効きます。

誰が何をするか
機械同じ実体の変数をまとめる（COMMONの位置・引数の対応など機械的な根拠だけで）。 コメント・FORMAT文・初期値などの「意味の手がかり」も収集する
AIその手がかりだけを根拠に意味（例:「年間税率」）を書く。 根拠が無いものは「不明」のまま残す（推測で埋めない）
あなた承認する（ここだけが人の仕事）

承認した意味は仕様書の入出力表に自動で転記されます （年間税率(比率) [V-0001] の形）。既定では、未承認の変数が残る関数は ①に進めません（急ぐ場合は「辞書のゲートを解除して」と言えば先へ進めます）。

⓪.5 変数辞書 (2/2) — 実際の手順

  1. 打つ（無人バッチ）: 
    /legacy-0-dict
    • 放置でよい（実行中でも次の承認を並行できる）。 様子を見ながら数十件だけ試したいときはチャットで /legacy-0-dict
  2. 起きること（あなたの操作なし）: AIが根拠から変数の意味を書き、 機械が検証して辞書ページ（進捗サイトの「変数辞書」）を更新する
  3. 承認する: ブラウザでナビバーの「変数辞書」を開く。 変数が「多くの関数で使われるもの・確認が要るもの」順に並んでいるので、上から:
    行の表示操作
    rank A / B（コメント等の根拠あり）意味を確認してチェック→一括承認
    rank C / D（根拠が弱い・無い）意味欄を直して「修正して承認」（1件ずつ）
    チャット派は「V-0001とV-0002を承認して」「V-0003は年間税率に直して承認して」でも同じ。
  4. 知らない変数はどうする？: 分からなければ放置でよい。 承認しない限り確定しない。まず上位（多くの関数に効くもの）だけ片付けて①へ進み、 残りは後から戻ってきてもよい
完了のサイン: 「変数辞書」ページの未承認が0件 （または AI が「dict-gate で止まる関数は無くなった」と報告）→ /legacy-1-spec へ。

① 関数仕様書 — まず1件お試し、あとは全件バッチ

  1. まず1関数だけお試し: /legacy-1-spec F-0001 （関数IDはWBSの推奨着手順の先頭から）。出てきた仕様書を読んで、規約や変数辞書の 効き方に問題がないか品質を確かめる。直したい傾向があればここで 規約・辞書を直してから全件へ
  2. 残りは全件バッチ: 
    python <LR>/scripts/pipeline.py spec --root .            # 全関数
python <LR>/scripts/pipeline.py spec --root . --flow 月次バッチ  # フローの範囲だけ
    夜に起動して寝てよい。機械レビュー通過済みの draft が溜まっていく
  3. あなたがやること: 一斉レビュー表（次ページ）で まとめて承認する。各項目の Confidence（🟢確認済 / 🟡推測 / 🔴仮定）が 目印。🟡🔴の質問には Yes/No で答える（答えられなければ「保留」でよい）
提示される仕様書は機械レビュー通過済み: 引用行の実在・記入漏れ・根拠なし🟢は機械が先に落としている。 あなたは「意味が正しいか」だけを見ればよい。 最終品質の上限はこのレビューの品質です——いちばん丁寧にやる価値がある場所。

②へは、①のレビューが終わってから進むのが基本形 （②は「①が承認済みの関数」しか対象にならないので、順序は仕組みでも守られる）。 書き直しは draft のうちは何度でも頼める。

一斉レビュー表 — まとめて承認する

draft になった仕様書が1枚の表に並びます（WBS の「要対応」からリンク）。

  • 並び順が優先度: 上から「そのまま承認できる」→「ISSUE がある」→ 「AI修正待ち」。判断が要らないものから片付けられる
  • 各行の「承認」「修正依頼…」でその場で完結。 関数名リンクから全文を読んでから決めてもよい
  • ❌の行は「AI修正待ち」と出る（AIの自己修正を待つ） （＝機械NGのものは人が承認できない）

チャットで「全部OK」「F-0003 は修正: 端数処理が書かれていない」 と返すやり方も、そのまま使える。

② テスト仕様書 — ①が全部承認できたら、②を全件

  1. 打つ（全件バッチ・②だけ）: 
    python <LR>/scripts/pipeline.py testspec --root . [--flow 月次バッチ]
    対象になるのは①が承認済み（reviewed）の関数だけ。未承認の関数が 勝手に進むことはない。1件ずつなら /legacy-2-testspec F-0001
  2. 起きること: AIが「①の仕様書だけ」からテストケースを 設計する（レガシー原文は見ない。①に書いていないことはテストにできない—— 仕様書の穴がここで露見する）
  3. あなたがやること:
    • ケース一覧（正常系・境界値・異常系…）を見る
    • 期待値が決められないケース（⚠未確定）の質問に答える
    • 問題なければ承認 → approved（⚠未確定が残ったままの承認は機械が拒否）

「全🟢仕様項目にテストがあるか」「①に無い仕様IDをでっち上げていないか」は 機械検証済み。あなたは期待値が業務的に正しいかだけを見る。

ここまでで人の承認は一通り終わり。③④⑤は承認ゲートが無いので、 次はまとめて流すだけです。

同じ指摘を2回したら — docs/prompts/ に1行足す

レビューで「またここか」と思ったら、それは指示を書く場所があるというサインです。 ①〜④は起動のたびにこの4ファイルを読んでから書き始めます （作り直し・改訂・無人バッチでも同じ）。

ファイル効く工程書くことの例
docs/prompts/1-spec.md① 仕様書 「漸化式は言葉で要約せず式で書く」「添字の基準を毎回明記」
docs/prompts/2-testspec.md② テスト仕様 「0近傍と負値は全関数で必ず1ケース」
docs/prompts/3-testcode.md③ テストコード 「fixture は conftest.py に集約」「比較は pytest.approx」
docs/prompts/4-impl.md④ 実装 「要素ごとの Python ループは避ける」「Decimal を float にしない」

どのファイルにも重点 / 用語の約束 / 繰り返さないでほしい指摘 / 手本にする成果物 の節が用意してあります。一番効くのは「手本」—— 「粒度は docs/specs/F-0123.md に揃えて」と1行書くほうが、抽象的な指示を10行書くより揃います。

使い分け
  • この1件だけ直したい → チャットで言う（書き足すと指示が太るだけ）
  • 毎回同じことを言っている → prompts の「繰り返さないでほしい指摘」に1行
  • 節そのものを増減したい → docs/templates/、規約なら conventions.md

書けるのは「どう書くか」だけです。読んでよい入力の制限・必須項目・承認の要否といった 土台の規則は変えられません（反する指示があっても AI は従わず、あなたに報告します）。

③④⑤ — 承認が終わったら、まとめて流すだけ

②の承認が済んだ関数は、③テストコード→④実装→⑤テストまで人の承認なしで 自動で進みます。全件流すには:

python <LR>/scripts/pipeline.py run --root . [--flow 月次バッチ]

run は「次に進められる工程」を関数ごとに自動判定するので、③④⑤を 分けて指定する必要はない（分けたければ --only testcode 等）。 1件ずつなら /legacy-3-testcode F-0001 / /legacy-4-impl F-0001。

③と④は見守るだけ。それぞれ独立に作られます:

③ テストコード入力は「②＋規約」だけ
⇄互いを見ない
④ 実装入力は「①＋規約」だけ
  • ③完了時にテストは freeze（ハッシュ記録）。以後AIがテストを書き換えようと しても hook が拒否する（「テストを緩めて通す」事故を仕組みで防ぐ）
  • ④のスタブ（空実装・TODO）は機械検知されるので「実装したふり」はできない
  • ④が「①だけでは決められない」と気づくと ISSUE を起票して止まる → あなたは質問に答えるだけ（①の改訂・伝搬は自動で面倒を見る）

⑤ の結果 — fail のときだけ、あなたの出番（裁定）

⑤はバッチ（run）が自動実行します（1件ずつなら /legacy-5-test F-0001）。 pass なら完了（WBS が ✅ になる）。fail のときだけ、あなたの出番:

分類原因あなたの操作
(a) 実装バグ実装が①を満たしていない何もしない（AIが修正→再実行を自走）
(b) テストのバグ③が②とズレているISSUE の証拠を見て承認 → ③再生成
(c) 仕様が誤り②①自体が間違いISSUE で裁定 → ①改訂を指示

(a) の自動修正は3回で自動停止し、WBS に ⛔ が出ます。AIの失敗分析 （何を試し、なぜ駄目で、(a)/(b)/(c)のどれと考えるか）が ISSUE に書かれているので:

  1. 仕様書ページ（またはバッチ画面の「人待ち」）に出ている質問に回答を書いて送る （記録・再開準備まで自動）
  2. そのあと /legacy-5-test F-xxxx（または pipeline.py run）で再テスト （チャットなら回答 →「アンブロックして」→ /legacy-5-test F-0001）
⛔ はあなたの回答待ちで完全に止まっている状態。見かけたら最優先で裁定する。 (b)(c) をAIが勝手にやることはない（テスト改変は hook が物理的に拒否）。

無人バッチの共通ルール — 中断・再開・順番の割り込み

ここまでに出てきた pipeline.py spec / run は、すべて同じ性質を持ちます:

  • いつ止めても安全、再開は同じコマンド。 Ctrl-C・電源断でも進捗は すべてファイル側にあり、もう一度同じコマンドを打てば続きから走る
  • レートリミット・利用枠上限は待って自動再開。 失敗扱いにせず 指数バックオフで待つので、夜間の利用枠リセットを人手なしで跨げる
  • 承認待ち・裁定待ちは自動でスキップして先へ進む＝ あなたが承認する速度が全体の速度。回しながら一斉レビュー表・ 「人待ち」タブで承認していく
  • 1関数=1つの新しいAIプロセスなので、何千件でもトークン上限に当たらない

よく使う操作:

python <LR>/scripts/pipeline.py run --root . --dry-run    # 実行せず対象と順番だけ確認
python <LR>/scripts/pipeline.py run --root . --max-funcs 20  # 今日は20件だけ
python <LR>/scripts/pipeline.py priority F-0012           # この関数を次に割り込ませる（実行中でも効く）
python <LR>/scripts/pipeline.py priority                  # ⭐割り込みの一覧（--off / --clear で解除）

実行中の様子はナビバー「バッチ状況」（/pipeline.html）で ライブに見える（表示専用）。次ページ参照。

ISSUE の答え方 — 白紙の質問は来ない

AIが判断に迷うと ISSUE（質問票）を起票します。必ず 「仮説＋Yes/Noで答えられる問い」の形で来ます。

  • 答え方は3通り、どれでも同じ: チャットで答える / ISSUE ファイルの「回答（人が記入）」欄に書く / review_actions.py adjudicate（⑤裁定）
  • 残すべき回答は AI が転記文を提案するので、あなたがドメイン知識集 （domain-knowledge.md）に貼れば同じ質問は二度と来ない
  • 未回答の ISSUE は WBS の最上部に出続ける。急がなくてよいが、 ⛔ が付いた関数はあなたの回答待ちで止まっている

⑥ 完了検証 / ⑦ 分析・改善 — 全関数が終わったら

⑥ /legacy-6-check — 全関数の①〜⑤・未回答ISSUEゼロ・実装率100%を 機械で総点検します（LLM不使用・数十秒。時期が来ると WBS トップに実行方法の案内が出ます）。

  • fail: 「どの関数の何が足りないか」の作業リストが出る → 該当フェーズのコマンドで埋めて再実行
  • pass: 最終成果物が出る — 仕様書一式のHTMLサイト、 関数仕様書・テスト仕様書・テスト結果報告書の3冊のPDF、API詳細（Sphinx）

⑦ /legacy-7-analyze — 移植完了後の高速化・リファクタリング。 まず機械が計測し（プロファイラ等）、AIは実測値だけを見て施策を提案、 あなたが施策票を承認すると適用されます。適用は「テスト全pass維持」が絶対条件なので、 ①〜⑤で作ったテスト資産がそのまま安全網になります。

⑦であなたがやること: 実データ規模の代表処理を流す bench.py を プロジェクトルートに用意する（python bench.py で一通り走るように）。 これで計測の質が決まる。あとは施策票の承認だけ。

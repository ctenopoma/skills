## テストケースIDの対応付け（⑤の実装率集計に必須）

- テスト関数には必ずマーカーで②のケースIDを付ける（1関数=1ケース）:

```python
@pytest.mark.tc("F0123-TC-001")
def test_calc_tax_normal_rounding_down(): ...
```

- ⑤の収集スクリプトは「②のケースID一覧」と「マーカー一覧」を突合して実装率を算出する。
  マーカーの無いテスト関数、②に存在しないIDのマーカーは、どちらも⑤でエラーとする

## docstring 規約（④・Sphinx napoleon 前提）

- Google スタイル。`Spec:` 行と `Side Effects:` セクションを必須とする
- `Side Effects:` は無い場合も「なし。」と明記（空欄と区別）

```python
def calc_tax(amount: Decimal, rate_code: str) -> Decimal:
    """税額を計算する。

    Spec: F-0123 / Legacy: CALC-TAX (tax.cbl:120-240)

    Args:
        amount: 課税対象額。
        rate_code: 税率区分コード。

    Returns:
        税額（切り捨て済み）。

    Side Effects:
        なし。
    """
```

## 禁止事項

- ③④の作業中にレガシー原文を読むこと（仕様の疑義は ISSUE 起票で解決する）
- ⑤ループ中に `tests/` 配下を編集すること（hook で拒否される。正規経路は ISSUE→人承認→③再生成）
- ④で**スタブを置いて先に進むこと**。`NotImplementedError`・`pass` だけの関数・`TODO`/`FIXME` コメントは
  静的チェックで検出され④は未完了扱いになる。①だけで実装しきれない場合は、その場で埋めずに
  **spec-gap ISSUE を起票して停止**する（下記フローで①が改訂されてから再開）

## 仕様不足時のフロー（④が詰まったとき）

1. ④は spec-gap ISSUE を起票して停止（何が決められないかを具体的に書く）
2. **①改訂エージェント**（レガシー原文を読む権限を持つ唯一の役割）が該当箇所を調査し、
   根拠（file:lines）と Confidence 付きで①を更新する
3. ハッシュ連鎖により②が「要再確認」に落ちる。テストへ影響する変更なら②再生成→人の再承認
4. ④を再開（更新後の①のみを入力とする。④自身は最後までレガシーを読まない）

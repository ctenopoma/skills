# Step 3: Skills × MCP 連携 — 手順書が道具を使う

> **ハンズオンは紙芝居版で**: [../../slides/a3-combo.html](../../slides/a3-combo.html) をブラウザで開く。
> この README は同内容のテキスト版(記録用)。

Step 1 で Skill(手順書)、Step 2 で MCP(道具)を作った。この章のポイントは1つだけ:

**連携に特別な仕組みは何もない。SKILL.md に「この MCP ツールをこの順で使え」と書くだけ。**

## 1. 役割分担のおさらい

| | 担当 | 例(この教材) |
| --- | --- | --- |
| **MCP サーバ** | データと操作(できること) | タスクの追加・一覧・完了 |
| **Skill** | ワークフロー(いつ何をどの順で) | 「作業分解 → 登録 → 進捗報告」の段取り |

MCP だけだと、Claude は道具を持っているが「良い作業計画の立て方」を知らない。
Skill だけだと、段取りは知っているがタスクを記録する場所がない。両方あって初めて
「この作業、タスクに分解して」の一言で計画立案から登録までが完了する。

## 2. ハンズオン: task-planner スキル

ToDo MCP(Step 2)を使う「作業分解プランナー」スキル。目標を与えるとタスクに分解して
登録し、「進捗まとめて」で進捗レポートを作る。
完成例: [examples/task-planner/SKILL.md](examples/task-planner/SKILL.md)

先に完成例を開いて、次の3点を確認してから写経する。

1. **ツールをフルネームで指名している**: Claude Code から見た MCP ツール名は
   `mcp__<サーバ名>__<ツール名>` (例: `mcp__todo__add_task`)。
   SKILL.md でこの名前を指名すれば、Claude は迷わずそのツールを使う
2. **LLM の判断とツール操作を組み合わせている**: タスクへの「分解」は LLM の仕事、
   「登録」はツールの仕事。手順書がその分担と順序を規定している
3. **人間の合意を挟んでいる**: 「分解案を提示して合意を得てから登録」というルールで、
   ツールの書き込み操作に人間のチェックポイントを置いている

セットアップ:

```bash
cp -r learning/level-a/03-skills-x-mcp/examples/task-planner ~/.claude/skills/
claude mcp list   # todo サーバが登録済みか確認(Step 2 でやった)
```

Claude Code を再起動して試す:

- 「グラフ描画の MCP サーバを作る。タスクに分解して」
  → 分解案の提示 → 合意 → `add_task` が件数分呼ばれる → 着手順の提案
- いくつか完了させたあとで「進捗まとめて」
  → `list_tasks` → 所定の形式のレポート

## 3. ここで理解しておくこと

- **疎結合**: サーバを SQLite 版に改造しても(Step 2 の改造課題)、スキルは無変更で動く。
  逆に分解の粒度やレポート形式を変えたいときはサーバに触らない。この分離が保守性の正体
- **description の連鎖**: 発動の流れは
  「ユーザーの依頼」→(Skill の description にマッチ)→「SKILL.md の手順」→
  (手順がツールを指名)→「MCP ツールの docstring を見て引数を組む」。
  つまり description と docstring の書き方が全体の品質を決める
- **MCP 側に手順を書かない**: サーバの docstring は「このツール単体の使い方」まで。
  複数ツールをまたぐ業務手順(分解の粒度、合意の取り方、レポート形式)は Skill に書く。
  逆転させると、サーバがクライアント固有の事情を抱え込んで他ツールから使いにくくなる

## 4. 改造課題

- Step 2 の改造課題(`due` 追加)と連動させ、計画時に期限も聞いて登録する
- 進捗レポートを Step 1 の daily-log スキルの当日ログにも追記させる
  (スキルがスキルの成果物を参照する例)
- 「分解の粒度ルール」を references/planning-rules.md に分離し、
  SKILL.md を触らずにルールを育てられる構成にする(Step 1 の段階的開示の応用)

## 5. 他ツールでの活用

- MCP サーバ(道具)はそのまま他クライアントでも使える(Step 2 §6)
- Skill(手順書)は、OpenWebUI 等ではシステムプロンプトに転用できる。ツール名の表記
  (`mcp__todo__add_task`)はクライアントによって変わるため、そこだけ読み替える
- つまり「道具は完全にポータブル、手順書はほぼポータブル(ツール名の方言だけ直す)」

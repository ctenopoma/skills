設計主題①: 大きいデータをコンテキストに入れない

CSV をそのまま Claude に読ませると、コンテキストを浪費するうえ、 行数が増えると集計を間違え始める。data-mcp はデータを LLM に見せないための道具。

ツール返すもの
loadDuckDB テーブルとして登録し、行数と型だけ返す
profile列ごとの欠損・ユニーク・代表値の要約
querySQL の結果(最大50行に制限。溢れたら「集計せよ」と促す)
export処理結果をファイルに書き出し、他ツールへはパスで渡す
原則: LLM に流すのは「要約と結果」だけ。生データはサーバ側に留め、 ツール間の受け渡しもファイルパスで行う。100万行でもコンテキスト消費は変わらない。

設計主題②: LLM に計算させない

検定統計量や交差検証スコアのような「答えが一意に決まる計算」を LLM が暗算すると、それらしい嘘が混ざる。stats-mcp はそれを潰すための道具。

  • compare_groups: 2群なら Welch の t 検定、3群以上なら ANOVA を自動選択
  • test_independence / correlation / check_normality: 定番の検定・相関を関数一発に
  • quick_fit: RandomForest+5-fold CV のベースライン。「予測できそうか」の当たり付け
設計の作法: ツールは数値と注意書きだけ返し、結論を断定しない (「p 値 = 0.03」までがツール、「差があると言えるか」の解釈は LLM と人間の仕事)。 期待度数不足や n 過大のときは警告を添える。

設計主題③: 手順と知識はスキルへ

eda-workflow/ ├── SKILL.md 手順6ステップ+ルール(暗算禁止・因果断定禁止 等) └── references/ ├── quality.md 品質チェックリストと対処の選択肢 ├── charts.md 伝えたいこと → 図の対応表+作法 └── methods.md 問い → 手法の選定フロー(=手法提案の中身)
  • 「2群で差があるか?」→ t 検定、「予測できそうか?」→ quick_fit、のように 問いから手法を引く表を references に持つ。手法名から入らない
  • p 値の扱い・多重比較・サンプルサイズの注意もここに書く — コードが1行もない、知識だけの本格スキル資産
  • チームの分析ノウハウが溜まったら references に追記するだけで全員に配れる

diagram スキル: ポンチ絵をテキスト記述に

「描画ツールでマウス作業」を「テキストで記述」に置き換える。 修正・バージョン管理・流用が楽になる。

  1. 図種を決める: 伝えたいこと→図種の対応表(フロー / 構成 / シーケンス / 状態遷移 / 因果 / ガント)
  2. 要素を箇条書きで合意: 描く前に箱と矢印を列挙してユーザーと確認(手戻り防止)
  3. 記法パターンで組む: Markdown・GitHub 向けは Mermaid、 単体ファイル・html-craft 埋め込みは SVG 直書き
作法: 箱は7個前後まで/流れの向きは1方向に統一/色は意味があるときだけ。 SVG パターンは html-craft と同じ配色トークンなので、スライドやダッシュボードに 貼っても馴染む。

ハンズオン: サンプルデータで一巡する

mcp-servers/data-mcp/sample/experiment.csv を分析して

eda-workflow が発動し、おおよそ次の流れで進む(数値は実測):

  1. load → 400行・5列。profile → temp に欠損12件を検出
  2. 品質チェックの報告 → 分布(histogram)→ correlation → dose と yield_pct に強い相関(r = 0.85)を発見、散布図で確認
  3. 深掘りの例:
    • 「group ごとに収率に差はある?」→ ANOVA(p = 8.8e-13、B群が高い)
    • 「収率は予測できそう?」→ quick_fit(R² ≈ 0.62、dose の重要度 0.88)
  4. 所見まとめ → 「レポートにして」で html-craft(dashboard)、 「分析の流れをポンチ絵にして」で diagram が接続する

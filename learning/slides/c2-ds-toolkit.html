ハンズオン1: 分析を一巡させて観察する

mcp-servers/data-mcp/sample/experiment.csv を分析して

模擬実験データ(400行: group, dose, temp, category, yield_pct)で eda-workflow が発動する。結果を読む前に、進み方を観察する:

  • ツールが load → profile の順で呼ばれているか (スキルの手順1→2)
  • 品質チェックの報告に temp の欠損が挙がっているか(12件仕込んである)
  • 会話の中にCSV の生データ(400行)が一度も現れないこと — 出てくるのは要約と最大50行の集計結果だけ

ハンズオン1: 答え合わせ

データは答えを仕込んで生成してある。自分の結果と突き合わせる:

チェック項目期待される結果
行数・列数400 行・5 列
品質temp に欠損 12 件(他の列は欠損なし)
相関dose と yield_pct に強い正の相関(r ≈ 0.85)
その他の関係temp は yield_pct とほぼ無相関(r ≈ -0.01)

数値が多少ずれるのは正常(集計の切り口の違い)。ただし 「dose が効いている」という発見に至らなかったら、どのステップで 見落としたかをログで遡る — それ自体が手順書のデバッグ。

ハンズオン2: 深掘りの質問を投げる

続けて聞く(1つずつ)。どのツールが選ばれるかを毎回確認する:

質問呼ばれるはずのツール期待される結果
「group ごとに収率に差はある?」compare_groups(3群→ANOVA自動選択)p ≈ 8.8e-13、B 群が高い
「収率は予測できそう?」quick_fitR² ≈ 0.62、dose の重要度 ≈ 0.88
「category と group に関連はある?」test_independencep ≈ 0.67 = 関連なし
3問目はわざと関連のない組み合わせ。「有意でない」を Claude が どう報告するかを見る — 無理に発見をひねり出さず「関連は確認できない」と 言えていれば、手順書のルール(断定しない・裏付ける)が効いている。

ハンズオン3: 分析の流れをポンチ絵にする

ここまでの分析の流れをポンチ絵にして。Markdown に貼れる形式で

観察ポイント(diagram スキルの手順どおりか):

  1. いきなり描かず、箱と矢印の箇条書きを提示して合意を求めてくるか
  2. 「Markdown に貼れる形式で」の指定で Mermaid が選ばれるか
  3. 出力された ```mermaid ブロックを .md ファイルに貼り、 エディタや GitHub でレンダリングされることを確認

余裕があれば: 「同じ図を単体ファイルでも」と頼み、SVG 版が ブラウザで開けることも確認する(色が html-craft の成果物と揃っている)。

ログで確認: この構成の設計原則3つ

ここまでの自分のセッションログから、次の3つの証拠を探す:

  1. 大きいデータをコンテキストに入れない: 400行の生データが会話に出た箇所は無いはず。data-mcp の query が 50行で打ち切る設計と、export がファイルパスで受け渡す設計を思い出す
  2. LLM に計算させない: p 値・相関係数・R² はすべて stats-mcp の返り値。Claude が暗算した数値がひとつでもあれば、それは設計への違反 (見つけたら報告の仕方を疑う)
  3. 手順と知識はスキルに: 「3群だから ANOVA」の判断は stats-mcp の自動選択+ eda-workflow の references/methods.md (問い→手法の表)から来ている。code ~/.claude/skills/eda-workflow/references/methods.md を開いて表を確認する

改造ハンズオン2: 自分のツールを新設する

お題: 外れ値検出ツールを stats-mcp に自分で追加する。仕様だけ見て書く。

作るもの仕様
detect_outliers(csv_path, column) IQR 法(Q1−1.5×IQR 〜 Q3+1.5×IQR の外を外れ値とする)で、 件数・境界値・外れ値の例(最大5件)を返す。判定基準(IQR法)を 返答に明記する(基準を隠さない)

ヒント: pandas の quantile(0.25) / quantile(0.75)。 docstring には「機械的な基準であり、除外の判断は原因調査とセットで」と書く。

  1. 実装 → 再起動 →「yield_pct に外れ値ある?」で試す
  2. 手順書側も更新: eda-workflow の references/quality.md の 外れ値の行に「detect_outliers で件数と境界を確認」と追記
  3. もう一度「このデータの品質チェックして」と頼み、新ツールが使われるか確認
これで「MCP ツールの新設 → 手順書への登録 → スキル経由での発動」を 一人で一周したことになる。自分の分野の定番計算も同じ型で足していける。

発展課題

  1. compare_groups に効果量(Cohen's d)を追加する (p 値だけでは効果の大きさが分からない、という methods.md の注意を道具側で支える)
  2. 「所見まとめを html-craft の dashboard にする」流れを一度通し、 定型化できそうなら eda-workflow の手順6に追記する
  3. 自分の分野の定番手法・判断基準を references/methods.md に追記する — references をチームの知識置き場として育てる第一歩
  4. 自分の実データ(CSV)で一巡させ、手順書に足りないステップを見つけて直す

ハンズオンで確認した設計原則

  • 大きいデータはコンテキストに入れない(要約と結果だけ流す)
  • 決定的な計算は LLM にさせない(ツールは数値まで、解釈から先が LLM)
  • 手順と知識はスキルの references に集約し、チームの資産として育てる

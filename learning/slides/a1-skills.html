Agent Skills
使い方・作り方

Skill は Claude への「手順書」。実体はただの Markdown。
この章では最小のスキルを手で書き、動かし、段階的に育てる。

→ キーで次へ / ← で戻る

Skill の仕組み — 置き場所

Claude Code は起動時に、次の場所から SKILL.md を探して読み込む。

置き場所スコープ
~/.claude/skills/<スキル名>/SKILL.md個人用(全プロジェクト共通)
<プロジェクト>/.claude/skills/<スキル名>/SKILL.mdそのプロジェクト専用
skills/ └── my-skill/ ├── SKILL.md ← これだけあれば動く ├── references/ ← (任意)詳細資料 └── scripts/ ← (任意)同梱スクリプト

スキルは起動時に読み込まれる。追加・変更したら Claude Code を再起動する。

SKILL.md の構造

frontmatter(name と description)+ 本文。これだけ。

SKILL.md 
---
name: my-skill
description: いつ発動してほしいかを書く。
  Claude はこの文を見て「使うか」を判断する
---

ここに手順を書く(ふつうの Markdown)
  • name: スキル名(フォルダ名と合わせる)
  • description: 発動条件。ここだけが常に Claude に見えている
  • 本文: 実際の手順。使うと判断されて初めて読まれる

いちばん大事な設計原則: 段階的開示

description常時コンテキストに載る
(軽い)
→発動と判断
SKILL.md 本文使うときだけ読む
→必要になったら
references/さらに詳しい資料

常に見えているのは description の1〜2文だけ。本文や資料は必要になった段階で読み込まれる。 これを 段階的開示 (progressive disclosure) と呼ぶ。

書き分けの指針:
・description には「何をするか」+「どんな依頼のときに使うか」を具体的に
・本文は多少長くても他のタスクの邪魔にならない(読まれるのは発動時だけ)
・さらに大きい資料は references/ に分け、本文から「必要なら読め」と誘導

ハンズオン1: 最小のスキルを作る

お題: コミットメッセージを Conventional Commits 形式で書かせる

ファイル1個で完結する最小構成。まずフォルダを作る。

mkdir -p ~/.claude/skills/commit-message

続いて ~/.claude/skills/commit-message/SKILL.md を自分で書いてみる。 次のページに完成例があるが、先に自分で書いてから見比べるのがおすすめ。

書く内容のヒント:

  • description: 「コミットメッセージを書いて」と言われたときに発動してほしい
  • 手順: ① ステージ済みの diff を確認 → ② 変更の種類 (type) を選ぶ → ③ 形式に沿って書く

ハンズオン1: 完成例

~/.claude/skills/commit-message/SKILL.md 
---
name: commit-message
description: git のコミットメッセージを Conventional Commits
  形式で作成する。ユーザーが「コミットメッセージを書いて」
  「コミットして」など、変更のコミットに関する依頼をしたときに使う。
---

# コミットメッセージ作成

## 手順
1. `git diff --staged` でステージ済みの変更を確認する
2. 変更内容から type を選ぶ:
   feat / fix / docs / refactor / test / chore
3. 次の形式でメッセージを作る:
   <type>: <変更の要約(50文字以内、言い切り形)>

## ルール
- 要約は「この変更で何がどうなるか」を書く
- 無関係な変更が混ざっていたらコミット分割を提案する

ファイル一式は learning/level-a/01-skills/examples/commit-message/ にもある。

ハンズオン1: 動作確認

  1. Claude Code を再起動する(スキルは起動時に読み込まれる)
  2. 適当なファイルを変更して git add しておく
  3. Claude に話しかける: 
    コミットメッセージ書いて
  4. スキルの手順どおり(diff を見る → type を選ぶ → 形式に沿う)に動けば成功
うまく発動しないときは description を疑う。
「ユーザーの依頼文」と「description の文面」が結びつくか?という観点で書き直す。 発動条件のチューニングがスキル開発の勘所。

ハンズオン2: references/ で拡張する

お題: 今日の作業ログを記録する daily-log スキル

ログのテンプレートが長くなるので references/ に分離し、段階的開示を体験する。

daily-log/ ├── SKILL.md ← 手順(短い) └── references/ └── format.md ← ログのテンプレート(長い)

完成例: learning/level-a/01-skills/examples/daily-log/。 これを ~/.claude/skills/daily-log/ にコピーして使う。

cp -r learning/level-a/01-skills/examples/daily-log ~/.claude/skills/

ハンズオン2: 分離のポイント

SKILL.md 本文にはこう書いてある。

3. ログの形式は references/format.md のテンプレートに従う
  • Claude は実際にログを書く段になって初めて format.md を読む
  • テンプレートを差し替えたいときも SKILL.md には触らなくて済む

動作確認

今日のログをつけて。MCP教材のStep1をやった

~/daily-logs/2026-07-22.md のような日付ファイルが、 format.md の形式どおりに作られれば成功。

ハンズオン3: OSS のスキルを使う

スキルは自作だけでなく、公開されているものを取ってきて使える。 公式のサンプル集が GitHub にある(git clone で取得できる)。

# 公式スキル集を clone(任意の作業フォルダで)
git clone https://github.com/anthropics/skills.git anthropic-skills

# 中を眺めて、使いたいスキルをコピー
ls anthropic-skills/
cp -r anthropic-skills/<スキル名> ~/.claude/skills/
  • 導入は「フォルダを置いて再起動」だけ。インストールという概念がない
  • 取ってきたスキルの SKILL.md を読むのが最良の教材。description の書き方、 references/ や scripts/ の使い方など、自作の手本になる

スキルの実体はただのフォルダなので、社内共有も「git リポジトリに置く」だけで済む。 このリポジトリ自体がその実例。

さらに先へ: scripts/ パターン

手順の中に「決まりきった処理」があるなら、スクリプトを同梱して SKILL.md から実行を指示できる。

4. 変換は scripts/convert.py を実行する:
   python scripts/convert.py <入力> <出力>
  • LLM に毎回コードを書かせるより速く、結果も安定する
  • 「判断は LLM、定型処理はスクリプト」という分担

フル活用の実例として、このリポジトリの quarto-typst-pdf/ は references/ + scripts/ + assets/ を備えた本格構成。 今日作った最小構成との差分を眺めると、スキルがどこまで育てられるかが分かる。

改造課題

  1. commit-message に「メッセージの言語をユーザーの使用言語に合わせる」ルールを足す
  2. daily-log のテンプレートに「明日やること」欄を足す
    • format.md だけの変更で済むことを確認する(段階的開示の効能)
  3. 自分の定型作業をひとつ選んでスキル化する
    • 週報、レビュー観点、環境構築手順など、「毎回同じ説明をしているもの」が狙い目

他ツールでの活用

Skill の実体は「発動条件つきの手順書 Markdown」。Claude Code 以外でも流用できる。

ツール使い方
Claude Desktop / claude.aiSkills 機能に同じ SKILL.md 形式でアップロードできる
OpenWebUI などのチャット UISKILL.md 本文をシステムプロンプトやカスタム指示に貼れば、同じ手順書として機能する(自動発動はないので常時適用 or 手動)
ツール固有の機能ではなく「手順の文書化」なので、資産として腐りにくい。 これが Skill の本質的な利点。

仕組みの最小理解

登場人物は3つだけ。

ホストClaude Code
Claude Desktop / OpenWebUI …
⇄プロトコル
MCP サーバツールとリソースを提供
するプログラム
→
データ・機能ファイル / DB / API …
  • サーバ: ツール(呼べる関数)やリソース(読めるデータ)を提供する
  • ホスト: サーバに「どんなツールがある?」と聞き、LLM の判断でツールを呼ぶ
ホスト側から見ると、MCP サーバを1個繋ぐたびに Claude の「できること」が増える。 サーバ側から見ると、一度書けばどの MCP 対応ツールからも使える。これが標準プロトコルの価値。

接続方式 (transport) は実質2つ

transport仕組み用途
STDIO ホストがサーバをサブプロセスとして起動し、標準入出力で会話 ローカル完結。いちばん簡単
Streamable HTTP サーバは独立した HTTP サーバとして動き、ホストが URL に接続 複数クライアントで共有、リモート配置
旧方式の SSE transport もまだ動くが、仕様上は非推奨 (deprecated)。 後継が Streamable HTTP なので、これから作るならそちらを選ぶ。

どちらも localhost 間の通信なら、プロキシ環境の影響を受けない。

ハンズオン1: OSS サーバを使う

お題: 公式 OSS の filesystem サーバを Claude Code に繋ぐ

npm があれば導入は1コマンド。

claude mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem ~/daily-logs

読み方: 「filesystem という名前で、npx … 以降のコマンドを STDIO サーバとして登録する」。最後の引数はこのサーバに許可するディレクトリ。

# 登録確認
claude mcp list

  1. Claude Code を起動し、/mcp と打つ → 接続状態とツール一覧が見える
  2. 話しかける:

OSS サーバの探し方・取り方

  • 公式カタログ: modelcontextprotocol/servers リポジトリ(GitHub)
  • npm / pip で配布されているものは npx / uvx で直接起動できる
  • 配布されていないものも git clone してソースから起動すればよい (登録コマンドの -- 以降を python path/to/server.py 等にするだけ)

チームで共有するなら .mcp.json

claude mcp add は既定では個人設定に入る。 プロジェクトのリポジトリで共有したい場合は、プロジェクト直下に .mcp.json を置く。

.mcp.json 
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "./data"]
    }
  }
}

リポジトリを clone した全員が同じサーバ構成を使える。 「スキルは skills/ フォルダ、MCP は .mcp.json」— どちらもリポジトリに置くだけで共有できる。

ハンズオン2: ToDo サーバを自分で書く(1/2)

ここが本題。完成品は見ずに、まず1本目のツールを写経する

作業フォルダに my-todo/server.py を作り、次を打ち込む (コピペせず打つ。docstring がそのまま LLM への説明になることを意識しながら):

my-todo/server.py 
import json
from pathlib import Path
from mcp.server.fastmcp import FastMCP

DATA_FILE = Path.home() / ".todo-mcp.json"
mcp = FastMCP("todo")

@mcp.tool()
def add_task(title: str) -> str:
    """新しいタスクを追加する。ユーザーが「〜をタスクに入れて」
    「TODO追加」などと言ったときに使う。

    Args:
        title: タスクの内容(短い1文)
    """
    tasks = json.loads(DATA_FILE.read_text(encoding="utf-8")) if DATA_FILE.exists() else []
    task_id = max((t["id"] for t in tasks), default=0) + 1
    tasks.append({"id": task_id, "title": title, "status": "open"})
    DATA_FILE.write_text(json.dumps(tasks, ensure_ascii=False), encoding="utf-8")
    return f"タスク {task_id} を追加した: {title}"

if __name__ == "__main__":
    mcp.run()  # 既定は STDIO
pip install "mcp[cli]"
claude mcp add todo -- python (my-todo/server.py の絶対パス)

Claude Code を再起動 →「タスク追加して: MCP教材のStep2」→ 動いたら次へ。

ハンズオン2: 残り2本は仕様だけ見て自分で書く(2/2)

今度はコードを見ずに、仕様から自分で実装する。 データの読み書きは add_task と同じパターンでよい。

ツール仕様
list_tasks(status: str = "open") status("open" / "done" / "all")で絞ってタスク一覧を文字列で返す。0件ならその旨を返す
complete_task(task_id: int) 該当タスクの status を "done" にして保存し、結果を返す。見つからない ID のときも エラーにせず「見つからない」と返す

ヒント(詰まったときだけ見る):

  • docstring には「何をするか」+「ユーザーがどう言ったときに使うか」を書く(add_task と同じ型)
  • STDIO サーバはコードを変えるたびに Claude Code の再起動が必要

書けたら再起動 →「いまのタスク一覧見せて」「1番終わった」→「99番終わった」(存在しないID)で試す。

ハンズオン2: 答え合わせ

動いたら、完成例 learning/level-a/02-mcp/todo-mcp/server.py を開いて 自分のコードと見比べる。差分から学ぶ観点:

  • docstring の粒度: 「いつ使うか」まで書けていたか。完成例は 「ユーザーが『#1終わった』と言ったときに使う」の水準まで書いている
  • +αの設計: 完成例は登録日・完了日も記録している。 あとで「今週やったこと」を聞けるようにするための布石 — ツールは使われ方を想像して作る
  • 読み書きの関数化: 完成例は _load / _save に分けている。 ツールが増えるほど効いてくる

/mcp でツール一覧を開き、自分の書いた docstring がそのまま説明文に なっていることも確認する。

ここまでで「MCP サーバを自分でゼロから書いて動かした」ことになる。 50行の壁の低さと、docstring が品質を決めることが体感できたはず。

ハンズオン3: 自分のサーバを HTTP 化する

STDIO と HTTP の差が「起動方法の差」でしかないことを、自分のコードで体験する

my-todo/server.py の末尾を、起動引数で切り替わるように書き換える(変更はこれだけ):

import sys  # 先頭に追加

if __name__ == "__main__":
    if "--http" in sys.argv:
        mcp.run(transport="streamable-http")
    else:
        mcp.run()
# ターミナル1: サーバを起動しっぱなしにする
python (my-todo/server.py) --http
INFO: Uvicorn running on http://127.0.0.1:8000

# ターミナル2: HTTP サーバとして登録し直す
claude mcp add --transport http todo-http http://127.0.0.1:8000/mcp

Claude Code から同じようにタスク操作できれば成功。データファイルは共通なので、 STDIO 版で入れたタスクがそのまま見える。ツール定義は1行も変えていない。

ここで理解しておくこと

ツール定義@mcp.tool() の関数たち
= サーバの本体
+
transportSTDIO / Streamable HTTP
= ただの配管
  • HTTP 化してもサーバのコード(ツール定義)は1行も変わっていない
  • 運用の違い: STDIO は「ホストが都度起動」なので登録だけで動く。 HTTP は「自分でサーバを立てておく」必要がある
  • HTTP 化すると複数のクライアントから同じサーバを共有できる(次のページの伏線)

改造課題

  1. add_task に期限 due: str = "" を足し、list_tasks で期限順に並べる
  2. delete_task ツールを足す
  3. 保存先を JSON から SQLite に変える
    • ツール定義(関数シグネチャと docstring)は無変更で済むことを確認する

改造したら Claude Code を再起動(STDIO の場合)またはサーバを再起動(HTTP の場合)して反映する。

他ツールでの利用

同じ server.py がそのまま他のクライアントでも使える。

ツール繋ぎ方
Claude Desktopclaude_desktop_config.json の mcpServers に command / args を追記(.mcp.json と同形式)
OpenWebUI管理画面の External Tools に HTTP 版の URL http://127.0.0.1:8000/mcp を登録。または mcpo で MCP → OpenAPI 変換して接続
Cursor など各ツールの設定ファイルに同様の command / url を書くだけ
ハンズオン3で HTTP 化したサーバは、Claude Code と OpenWebUI から同時に使える。 「一度書けばどこからでも」を実際に確かめられる。

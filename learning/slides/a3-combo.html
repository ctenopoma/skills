役割分担のおさらい

担当この教材での例
MCP サーバデータと操作(できること)タスクの追加・一覧・完了
Skillワークフロー(いつ何をどの順で)「作業分解 → 登録 → 進捗報告」の段取り
  • MCP だけ → 道具は持っているが「良い作業計画の立て方」を知らない
  • Skill だけ → 段取りは知っているがタスクを記録する場所がない
  • 両方 → 「この作業、タスクに分解して」の一言で計画立案から登録まで完了

連携の正体: ツールをフルネームで指名する

Claude Code から見た MCP ツールの名前は次の形式。

mcp__todo__add_taskmcp__<サーバ名>__<ツール名>

SKILL.md の手順の中でこの名前を指名すれば、Claude は迷わずそのツールを使う。

3. 分解案を一覧で提示し、ユーザーの合意を得る
4. 合意後、mcp__todo__add_task で1件ずつ登録する
5. 着手順と「最初の一歩」を提案する
「分解」は LLM の判断、「登録」はツールの操作。 その分担・順序・チェックポイントを規定しているのが手順書。 サーバは作業計画のことを何も知らない。

ハンズオン: task-planner を自分で書く

~/.claude/skills/task-planner/SKILL.md を新規作成し、 次の仕様を満たす手順書を自分で書く(完成例は次ページで答え合わせ):

要素仕様
description「タスクに分解して」「作業計画を立てて」「進捗をまとめて」の言い回しで発動する
計画モード目標を確認 → 2〜7個のタスクに分解(半日以内の粒度・動詞で言い切る)→ 分解案を提示して合意を得てから mcp__todo__add_task で1件ずつ登録 → 着手順を提案
進捗モードmcp__todo__list_tasks を status="all" で呼び、 「完了 / 残り / 次の一歩」の形式でまとめる
ルール合意前に登録しない / タスクの文言を書き換えない / 未完了6件超で見直しを提案

書き方のポイント: MCP ツールはフルネーム (mcp__サーバ名__ツール名)で指名する。手順の番号と形式を具体的に書くほど動きが安定する。

設計原則: 疎結合を保つ

1. サーバとスキルは独立に差し替えられる

  • サーバを SQLite 版に改造しても(Step 2 改造課題)、スキルは無変更で動く
  • 分解の粒度やレポート形式を変えたいときはサーバに触らない

2. MCP 側に業務手順を書かない

  • サーバの docstring は「このツール単体の使い方」まで
  • 複数ツールをまたぐ業務手順(分解の粒度、合意の取り方、レポート形式)は Skill に書く
逆転させると、サーバがクライアント固有の事情を抱え込み、 他のツールから使いにくくなる。「道具は汎用、手順は個別」を守る。

改造課題

  1. Step 2 の改造課題(due 追加)と連動させ、計画時に期限も聞いて登録する
  2. 進捗レポートを Step 1 の daily-log スキルの当日ログにも追記させる
    • スキルがスキルの成果物を参照する例。SKILL.md にどう書けば安定するか考える
  3. 「分解の粒度ルール」を references/planning-rules.md に分離する
    • SKILL.md を触らずにルールを育てられる構成(Step 1 の段階的開示の応用)

他ツールでの活用と、レベルAの締め

部品可搬性
MCP サーバ(道具)完全にポータブル。どの MCP 対応ツールでもそのまま(Step 2 §他ツール)
Skill(手順書)ほぼポータブル。システムプロンプト等に転用できるが、ツール名の表記(mcp__todo__add_task)だけクライアントの方言に読み替える

レベルAで学んだこと

  • Skill = 手順書(SKILL.md、段階的開示、description が命)
  • MCP = 道具箱(OSS 利用 → 内製50行 → transport は配管)
  • 連携 = 手順書に道具の名前と使う順番を書くだけ。判断は LLM、操作はツール、合意は人間
次のレベルBでは、道具の入出力をテキスト以外(画像・PDF)に広げる。 レベルCでは、手順書を「複数エージェントの分業設計」に育てる。

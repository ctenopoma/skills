教材のレベルA〜Cは「作る」「試す」まで。この付録は右半分の話。

先に大事な整理: Skill はクライアント側のファイル、MCP はサーバ。 だから配布の仕組みがまったく違う(次の2枚)。

Skills の配布 = ファイルを配る問題

形態やり方向き
個人用を git 共有~/.claude/skills を git リポジトリにする(このリポジトリ方式)個人の複数PC、少人数
プロジェクト同梱<repo>/.claude/skills/ に入れてコミットそのプロジェクトの全員
Claude Code プラグインスキル・コマンド・MCP設定を束ね、マーケットプレイスとして配布。利用者は /plugin で導入。マーケットプレイスの置き場は git リポジトリ、または LiteLLM の Skills Gateway(社内レジストリ機能)部署・組織への本格配布
どの形態でも、実行時にスキルを読むのは各自の PC(インストールした 手元のコピー)。Skills Gateway の詳細は9枚目。

MCP サーバの配布 = 4形態

形態やり方特徴
① ソース+gitclone して python server.py を登録(教材方式)一番単純。環境構築は利用者任せ
② パッケージpip / npm で配布し uvx / npx で実行依存ごと隔離実行。ミラーがあれば楽
③ Dockerイメージ化して実行(STDIO or HTTP)依存を完全に封じる
④ 中央ゲートウェイHTTP で1箇所に立て、全員が URL を登録各PCへのインストール不要

④は教材の --http の延長。②は pyproject.toml の [project.scripts] でエントリポイントを切ると uvx your-mcp-server の一発で配れる。

LiteLLM Proxy — 社内 LLM ゲートウェイ

OSS の LLM ゲートウェイ。社内に1台立てて、全員がそこ経由で LLM API を使う構成にする。 プロキシ環境の社内 AI 基盤として定番。

  • 仮想キー: 本物の API キーはゲートウェイだけが持つ。利用者には仮想キーを発行
  • コスト管理: ユーザー/チーム別の使用量集計・予算・レート制限
  • モデル振り分け: 複数プロバイダを1つの OpenAI 互換 API に集約

LiteLLM の MCP Gateway — MCP の一元配布

近年の LiteLLM には MCP ゲートウェイ機能があり、MCP サーバを ゲートウェイに登録して配布できる。

  • 利用者はゲートウェイの MCP エンドポイント1つをクライアントに登録するだけ
  • どのツール群を誰に見せるかを仮想キー単位でアクセス制御できる
  • ツール呼び出しのログ・監査もゲートウェイに集まる
位置づけ: 「HTTP化(レベルA ハンズオン3)」を組織規模にしたもの。 内製 MCP サーバの社内配布の本命。

機能の有無・設定記法はバージョン依存が大きい領域。導入時に必ず当該バージョンのドキュメントで確認する。

ハンズオン: LiteLLM を手元で立てる

pip install "litellm[proxy]"

作業フォルダに設定ファイルを作る:

litellm-config.yaml 
model_list:
  - model_name: claude
    litellm_params:
      model: anthropic/claude-sonnet-4-6
      api_key: os.environ/ANTHROPIC_API_KEY

general_settings:
  master_key: sk-handson-1234        # お試し用の管理キー

mcp_servers:
  data:                              # レベルC-2 で作った data-mcp をぶら下げる
    url: http://127.0.0.1:8000/mcp
    transport: http
# ターミナル1: data-mcp を HTTP で起動
python mcp-servers/data-mcp/server.py --http

# ターミナル2: LiteLLM を起動
PYTHONUTF8=1 litellm --config litellm-config.yaml --port 4000
Windows の日本語環境では PYTHONUTF8=1 が必須 (無いと起動バナーが cp932 でエンコードできず起動失敗する)。 PowerShell では $env:PYTHONUTF8="1"。

ハンズオン: ゲートウェイの認証と MCP 中継を試す

① 仮想キー認証の体験(キーが無いと通らないことを確認):

curl http://127.0.0.1:4000/v1/models
→ 拒否される
curl -H "Authorization: Bearer sk-handson-1234" http://127.0.0.1:4000/v1/models
→ {"data":[{"id":"claude",...}]} が返る

② MCP Gateway 経由で自作サーバを使う:

claude mcp add --transport http gw http://127.0.0.1:4000/mcp \
  --header "Authorization: Bearer sk-handson-1234"
  • 再起動して /mcp → gw が Connected。ツール名が data-load のように「サーバ名-ツール名」で見える (ゲートウェイが複数サーバを束ねるための名前空間)
  • 「experiment.csv を load して」→ ゲートウェイ経由で実呼び出しできる
  • 終わったら後片付け: claude mcp remove gw(直登録の data と重複するため)

LLM 中継そのもの(チャット補完)を試すには本物の API キーが必要。 キーがあるなら model_list のキーを本物にし、クライアントの接続先 (ANTHROPIC_BASE_URL 等)を http://127.0.0.1:4000 に向ける。

LiteLLM Skills Gateway — スキルの社内配布レジストリ

LiteLLM には、スキルの社内配布所(レジストリ)になる機能がある。 3枚目のプラグイン配布で使うマーケットプレイスの置き場を、 git リポジトリの代わりに LiteLLM が担うもの。

作る人スキルを登録・公開
POST /claude-code/plugins
→
LiteLLM社内スキルハブ
(一覧・検索・公開管理)
→
使う人/plugin marketplace add で追加
→ インストールして手元で実行
  • スキルの保存(マスター)は LiteLLM 側。チーム共有は 「登録 → 公開 → 各自がインストール」の流れで実現する
  • 実行時に読まれるのは各自の PC にインストールされたコピー。 リモート参照ではなく、アプリストアと同じモデル
  • Anthropic は関与しない。Claude Code のプラグイン配布の仕組みに、 社内向けの置き場を提供しているだけ
位置づけ: MCP Gateway が「MCP サーバの社内配布」なら、Skills Gateway は 「スキルの社内配布」。ゲートウェイ1台で LLM アクセス・MCP・スキルの 配布をまとめられる。

MCP Inspector — 内製開発の必携デバッガ

npx @modelcontextprotocol/inspector python server.py
  • ブラウザの GUI が立ち上がり、ツール一覧・呼び出しテスト・resources 閲覧ができる
  • docstring がどう見えているか、引数スキーマが意図どおりかを目視確認できる
使いどころ: Claude Code に繋ぐ前に Inspector で叩く。 動かないとき「サーバの問題か、クライアントの問題か」を一発で切り分けられる。 教材レベルBの改造課題をやるときにも便利。

FastMCP 2.x と uv/uvx

FastMCP 2.x(jlowin/fastmcp)

  • 教材で使った公式 SDK 同梱の FastMCP の発展版 OSS
  • 認証、複数サーバの合成 (mount)、既存サーバのプロキシ化、クライアントライブラリなど
  • 使い分け: 学習・小規模運用は mcp[cli] で十分。 認証付きで公開する段階になったら検討

uv / uvx

  • Python の高速パッケージマネージャ。uvx は「インストールせず隔離実行」
  • MCP サーバの配布・実行の事実上の標準になりつつある(Node 側の npx に対応)

# レベルC: 本格スキル開発 — 業務を置き換えるスキルを作る

> **ハンズオンは紙芝居版で**: [../slides/c1-skill-dev.html](../slides/c1-skill-dev.html) をブラウザで開く。
> この README は同内容のテキスト版(記録用)。

レベルA・Bで部品(手順書と道具)の作り方は身についた。レベルCの主題は
**「業務をひとつ置き換える規模のスキル」をどう設計するか**。
このリポジトリの [html-craft](../../html-craft/) を実例に、作る過程を一部始終見ていく。

## 1. 題材の選び方: ツール導入型スキル

狙い目は「既にやっている業務」×「便利だと知っているが、導入・学習コストで
使えていないやり方」の交点。面倒な部分をスキルに吸収させ、良いやり方だけを手に入れる。

| 実例 | 置き換える業務 | 吸収した面倒 |
| --- | --- | --- |
| quarto-typst-pdf | 技術文書のPDF作成 | Quarto/Typst の環境構築・記法・調整 |
| **html-craft** | スライド作成 / データ共有 / 口頭での原理説明 | HTML/CSS/JS の設計、自己完結化、PDF化 |

html-craft の発想: PowerPoint・Excelスクショ・口頭説明を、
**ブラウザで直接開ける自己完結HTML 1ファイル**(スライド / ダッシュボード / デモ)に置き換える。
変換ツールを介さず LLM が直接デザインするので自由度が高く、配布は「ファイルを渡すだけ」。

## 2. 要件を先に固める

コードより先に「成果物の条件」を文章にする。html-craft の場合:

- HTML 1ファイルで完結(CDN・外部フォント・fetch 禁止 = オフラインで開ける)
- 3モード(slides / dashboard / demo)をユーザーの言い方から判定する
- ブラウザ確認を経てから完成とする。PDF 化もできる

この要件がそのまま SKILL.md の「ルール」節になる。

## 3. 構成要素マップ — どこに何を置くか

本格スキルの設計は「知識と処理の置き場所の設計」。判断基準:

| 置き場所 | 置くもの | html-craft では |
| --- | --- | --- |
| SKILL.md | 常に必要な判断(モード判定)と手順の骨格 | モード判定表+6ステップ |
| references/ | モード別・状況別の詳細知識(必要時だけ読む) | design.md(共通原則)+ slides / dashboard / demo.md |
| assets/ | 実証済みの部品(ゼロから書かせず流用する) | deck.css / deck.js / page.css |
| scripts/ | 毎回同じで、LLMにやらせると遅い・不安定な処理 | new_page.py(雛形生成)/ to_pdf.py(PDF化) |

- **references はパターン集にする**: 「構成の型」「悪い例→良い例」「使える部品の一覧」。
  LLM への指示書なので、背景説明より判断基準を書く
- **assets は実績のあるものを転用する**: html-craft の CSS/JS は、この教材の紙芝居で
  実際に使って磨いたものをそのまま持ってきた。ゼロから書かせない
- **scripts は「決定的にしたい処理」だけ**: 雛形の組み立てや Edge 呼び出しは
  毎回同じであるべき処理。逆にデザイン判断はスクリプト化しない

## 4. description の設計(統合スキルの発動)

3モードを1スキルに統合したので、description に**全モードのトリガー語**を入れる:

> 「スライド作って」「発表資料」「紙芝居」「ダッシュボード」「データを見られるページ」
> 「デモ/シミュレータ作って」「HTMLで資料化して」…

モードの判定自体は SKILL.md 本文の表(意図→モード→必読 references)で行う。
「発動は description、分岐は本文」という分担。

## 5. scripts 開発で踏んだ実話: Edge の非同期書き出し

to_pdf.py(Edge ヘッドレス印刷)は、そのまま書くと**動かないことがある**:

1. 既定プロファイルだと起動済みの Edge に処理が委譲され、すぐ制御が返る
   → `--user-data-dir` で専用プロファイルを指定して回避
2. それでも Edge はプロセス終了の数秒後に PDF を書き出すことがある
   → ファイル出現をポーリングして待つ

道具のクセはこうやってスクリプトに封じ込める。LLM に毎回この回避策を
思い出させるのではなく、**一度だけ解いてコードに焼く**のが scripts の役割。

## 6. マルチエージェント: 大型デッキの分担執筆

15枚を超えるスライドは分担が速い(references/slides.md に手順を収録):

1. **親がアウトラインを確定**し、ユーザーと合意する(ここは分担しない)
2. 章ごとにサブエージェントへ「主張・材料・トーン・使ってよい部品」を指示し、
   スライド断片(`<section class="slide">`)を並列で書かせる
3. **一貫性の担保は親の仕事**: 用語・デザイン・粒度を揃え、重複を削り、枚数を刈る

勘所は「サブエージェントは文脈を共有しない」こと。書式ルール(1枚1メッセージ、
タイトルは要約文)を**毎回の指示に含める**。親が楽をするとデッキがバラバラになる。

## 7. ハンズオン: html-craft を使う

スキルは既にこのリポジトリにある(= `~/.claude/skills/html-craft/`)。再起動して:

- slides: 「レベルAで学んだことを5枚のスライドにして」
- dashboard: 「learning/level-b/plot-mcp/sample/timeseries.csv をダッシュボードにして。
  センサー切替できるように」(データ埋め込みと SVG 手描きグラフを確認)
- demo: 「移動平均の窓幅で滑らかさが変わるデモを作って」
- PDF化: 「いまのスライドをPDFにして」→ scripts/to_pdf.py が呼ばれる

## 8. 発展課題(レベルA・Bの部品と組み合わせる)

- **調査報告パイプライン**: paper-library-mcp で検索 → 文献ごとにサブエージェントで
  要約 → 比較統合 → html-craft(slides)で報告資料に
- **解析報告パイプライン**: plot-mcp で図を量産 → base64 で dashboard に埋め込み
- 自分の業務からツール導入型スキルの題材をひとつ選び、§3 の構成要素マップを
  埋めてから作り始める

## 9. カリキュラムのまとめ

- **A**: Skill = 手順書、MCP = 道具箱、連携 = 手順書に道具の名前を書くだけ
- **B**: 入出力はテキストに限らない。バイナリはサーバでコンテンツ型に変換。tools と resources
- **C**: 本格スキル = 知識と処理の置き場所の設計(SKILL.md / references / assets / scripts)。
  マルチエージェントは「親が輪郭と一貫性、サブが並列作業」

ここまでの成果物(ToDoサーバ、plot-mcp、paper-library-mcp、html-craft)は
すべてそのまま業務で使える。教材はここで完了。

# 執筆支援 — Markdown をPDF向けに整える判断基準

素のMarkdownは情報として正しくても、PDFにすると「ただの地の文が延々と続く」
「重要な注意がどこにあるか分からない」「コマンドと説明文の境目が曖昧」といった
読みにくさが出る。ここでは、原稿を読みやすく整形する際にどう判断するかをまとめる。
機械的なチェックリストではなく、**判断に迷ったときにどちらを選ぶか**の基準として使う。

前提として、この作業は**組版の提案**であって**編集**ではない。やっていいのは
「地の文を callout で囲む」「コマンドをコードブロックにする」「見出しを割る」
といった**入れ物を変える作業**だけで、**中身の文章を書き換えることではない**。
迷ったら「やってはいけないこと」を先に読む。

## callout の使い分け

Quarto の callout は5種類(note / tip / important / caution / warning)あるが、
色と強さが違うだけで、意味的な線引きは著者の意図次第になりがちなので、実務では
次の基準で選ぶ。

- **note** — 補足情報。読み飛ばしても本文の理解に支障が出ない背景説明、
  用語の言い換え、参考リンクの案内。原稿の「(補足)」「※」で始まる一文や、
  本文から浮いている一言メモは note の候補になる。
- **tip** — やると得すること。ショートカット、代替手段、パフォーマンス上の
  工夫など、「知っていると得だが知らなくても進める」情報。
- **important** — 読み飛ばすと後で詰まること。前提条件、依存関係、
  「先にこれをやっておくこと」。tip との違いは、無視したときに読者が
  困るかどうか。困るなら important、困らないなら tip。
- **caution** — 操作を誤ると手戻りが起きること。破壊的なコマンド、
  取り消せない設定変更、順序を間違えると失敗する手順。
- **warning** — 実害が大きいこと。データ消失、セキュリティ、
  本番環境への影響など、caution よりも一段深刻なもの。

迷ったときは note 寄りに倒す。強い callout(caution / warning)を乱用すると
本当に重要な箇所が埋もれて、結果的に何も強調していないのと同じになる。
1ページに caution / warning が3つも4つも並ぶなら、大半は important か
本文に戻すべきサイン。

Zenn の `:::message` は note、`:::message alert` は warning に機械変換される
(`scripts/zenn.py` 参照)。これは記法の対応関係であって意味の格上げではないので、
変換後に「本当に warning 相当の重さか」を一度読み直すとよい。Zenn では
alert を「ちょっと強めの注意書き」程度に軽く使っている記事も多く、そのまま
warning にすると必要以上に威圧的になることがある。

## コードブロックにすべきもの

判断基準は「読者がそのまま打つ・貼る・見比べる可能性があるか」。具体的には
以下は原則コードブロックにする。

- **コマンド。** シェルコマンド、CLI引数。地の文に埋め込むと、周囲の句読点や
  全角文字とコマンドの区別が付かなくなる。
- **パス・ファイル名・識別子。** `C:\Users\...` のような絶対パス、
  設定キー名、環境変数名。特に日本語の地の文にバックスラッシュや英数記号が
  混じると、フォントの影響で読み違えやすい。
- **設定値・設定ファイルの中身。** YAML/TOML/JSON の断片、`.env` の例。
  そのまま丸ごとファイルの内容と分かるようにする。
- **ログ・エラーメッセージ・実行結果。** 「〜というエラーが出る」ではなく、
  実際の文言をそのまま入れる。要約すると検索性が落ちる(読者はエラー文言で
  検索することが多い)。

逆に、地の文中で1語だけ触れる技術用語(「`pip` を使って」程度)まで全部
コードブロックにする必要はない。インラインコード(`` `like this` ``)で足りる。
段落の大半がインラインコードだらけになるなら、それはコードブロックに
出すべき内容が地の文に埋もれているサインなので、抜き出す方を検討する。

ファイル名が分かっている場合は、コードブロックの直前に太字でファイル名を
一行添える(`scripts/zenn.py` の変換もこの形にしている)。Quarto の
`{.lang filename="..."}` 属性は Typst 出力では表示されないことを実機で
確認済みなので使わない。

## 表にすべきか、箇条書きにすべきか

- **列の意味が全項目で揃っているなら表。** 「名前・型・既定値・説明」のように
  各項目が同じ属性を持つ並びは表にすると比較しやすくなる。
- **項目ごとに書く分量がバラバラなら箇条書き。** 表にすると1マスだけ
  異様に長くなり、列幅の自動調整が崩れて読みにくくなる
  (`references/pitfalls.md` の列幅の落とし穴も参照)。
- **手順・順序があるなら番号付きリスト。** 表は「同時に見比べる」ためのもので、
  「順に実行する」手順を表にすると、読者は上から下に読むのか列ごとに読むのか
  迷う。
- **2列で、片方が短いラベルなら表よりも定義リスト的な箇条書き(太字ラベル+説明)
  の方が収まりが良いことが多い。** 表にすると罫線の分だけ余白を食う。

迷ったら箇条書きに倒す。表は列数が増えるほどA4の横幅で崩れやすく、
崩れたときの直しがコード側では効かない(Typst側の列幅調整が要る)ため、
必要性が明確なときだけ使う。

## 図表キャプション

Quarto は **キャプションが付いている図・表だけを「浮動体」として扱い、
番号を振る**。キャプションの無い画像やベタの pipe table は本文の一部として
そのまま流れるだけで、「図1」「表1」のような参照可能な番号が付かない
(`filters/numbering.lua` が拾うのもキャプション付きのものだけ)。

したがって、**本文から「上の図の通り」「次の表を見てください」のように
指し示す図表には、必ずキャプションを付ける**。指し示さない、単なる挿絵的な
画像やちょっとしたメモ表には無理に付けなくてよい。

キャプションの文言は「何を示しているか」を一言で言い切る体言止めにする。
「〜についての説明」のような曖昧な言い回しより、「HACOのネットワーク構成」
「主要パラメータの比較」のように、キャプションだけ読んでも図表の中身が
推測できる言葉を選ぶ。

## 長い段落の分け方、見出しの粒度

- **1段落1論点。** 「〜だが、一方で〜であり、さらに〜のため」と接続詞で
  3つ以上の話題をつないでいる段落は、話題の変わり目で改行する。
  日本語の技術記事はどうしても一文が長くなりがちなので、文を割るより先に
  段落を割ると読みやすさが上がりやすい。
- **見出しは「本文を検索するときの目印」になる粒度で刻む。** 数段落に1回は
  見出しが来るくらいが目安。逆に、1〜2文しかない節に見出しを付けると
  目次が間延びする。
- **見出しの文言は本文を要約した名詞句にする。** 「〜について」で終わる
  見出しは、実質「この節のテーマ」を言っているだけで検索の役に立たないことが
  多いので、可能なら「〜の設定方法」「〜が遅い原因」のように具体化する
  (ただし、これは原稿の言い換えの範囲であって、意味を変える書き換えではない
  ことを確認すること)。
- **見出し行は必ず行頭(列0)に置く。** Zenn の記事ではリストの続きとして
  半角スペース付きで見出しを書いているケースが実在するが、GitHub側の表示は
  許容しても Quarto(Pandocのmarkdownリーダー)は列0の `#` しか見出しとして
  認識せず、そのまま地の文として埋もれる。手で見出しを追加・編集するときは
  インデントを付けないこと(`scripts/zenn.py` は既存原稿のこの形を自動で
  正規化するが、新規に書き足す分は自分で気を付ける必要がある)。

## やってはいけないこと

- **原文の意味を変える書き換えをしない。** 語順を整える、句読点を足す、
  箇条書きに割るといった「入れ物」の調整はよいが、主張の強さやニュアンスを
  変える言い換え(「かもしれない」を「である」にする、断定を弱める/強める)
  はしない。
- **事実を足さない。** 「なぜなら〜」「これは一般に〜」のような補足説明を
  読みやすさのために付け加えない。読者が知りたいのは著者が書いたことで、
  組版担当が推測したことではない。分からない箇所は分からないまま残す。
- **勝手に要約しない。** 長い段落を「分ける」のはよいが、「まとめる」のは
  別の作業。文章量を減らす提案をするときは、削ってよいか必ず確認を取る。
- **見出し・キャプション・callout のタイトルを新設するときは、本文中の
  既存の言葉から取る。** 存在しない言葉で新しい主張をしているように
  読めるタイトルを付けない。
- **表に整形するときに数値や項目を並べ替えない。** 表は見やすくするための
  入れ物であって、原稿の順序に意味がある場合(手順、時系列、優先順位)は
  その順序を保つ。

判断に迷ったら、変更前後を並べて「入れ物が変わっただけで、これを声に出して
読んだら元の文章と同じことを言っているか」を自問する。同じでなければ、
それは組版の調整ではなく編集になっている。
